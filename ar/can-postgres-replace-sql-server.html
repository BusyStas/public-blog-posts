يتناول هذا المقال اختيار قاعدة بيانات لمشروع جديد يبدأ من الصفر. الجواب المختصر: كمحرك لقواعد البيانات، Postgres جيد. أما كمنصة عمل متكاملة، فالأمر يعتمد على سير عمل CI/CD لديك وعلى الأدوات التي تحتاجها حول قاعدة البيانات.

هكذا أفكر بعد ثلاثة عقود من بناء البرمجيات على جانبي هذا السور.

السؤال الكامن خلف السؤال

"بأي قاعدة بيانات أبدأ؟" هو في الحقيقة ثلاثة أسئلة:

  • ما المهمة؟ لا أحد يدفع ثمن SQL Server لمجرد تخزين البيانات. نستخدمه للعمل مع البيانات: الإجراءات المخزنة، والتحويلات القائمة على المجموعات، والمهام المجدولة، وETL والتقارير، مع منطق الأعمال الذي يعمل بجوار البيانات مباشرة. حدّد أولاً هذا الحمل، ثم اسأل هل يستطيع Postgres القيام به.
  • هل يمتلك القدرات التي أحتاجها؟ الميزات التي يعتمد عليها حملي اليوم: الإجراءات، والجدولة، وETL، والتقارير، والأمان، والأدوات. لا أحد يختار قاعدة بيانات ليتمكن من مغادرتها لاحقاً، فالاختبار هو هل تفعل ما أحتاجه الآن.
  • كم تكلف؟ هذا ينتج عن الجوابين الأولين، لأن المهمة هي التي تحدد المعادلة. الحمل الثابت الثقيل يُسعَّر بعدد أنوية المعالج التي تُبقيها قيد التشغيل. أما الحمل المتقطع فيُسعَّر بعدد مرات الاستدعاء وثقل كل مهمة، وهنا قد تتفوق الشرائح التي تُحاسِب بحسب الاستخدام أو الشرائح عديمة الخادم (serverless). وتأتي التراخيص والاستضافة والعنصر البشري فوق ذلك.

الأمر يعتمد على المهمة. تخزين البيانات والاستعلام عنها: سهل. العمل مع البيانات داخل قاعدة البيانات: يتعامل Postgres جيداً مع SQL والشيفرة الإجرائية، لكن ليس مع المنصة المحيطة به (الجدولة وETL والتقارير). السؤال الثاني يُظهر في أي جانب يقع حملك. والثالث، التكلفة، ينتج عن الأولين: أنت تدفع إما مقابل معالج يعمل دائماً أو مقابل عدد مرات استدعاء قاعدة البيانات وثقلها.

أين يقف Postgres الآن

صدر PostgreSQL 18 في 25 سبتمبر 2025. أبرز ما فيه نظام فرعي جديد للإدخال والإخراج غير المتزامن، وقد أظهر بحسب المشروع قراءات أسرع حتى 3 أضعاف من وحدة التخزين. كما يحتفظ بإحصاءات المخطِّط عبر ترقيات الإصدارات الرئيسية، ما يزيل أحد أكثر حالات التباطؤ إزعاجاً بعد الترقية. ومن الإضافات الموجهة للمطورين الأعمدة المولَّدة الافتراضية، وuuidv7()، ومصادقة OAuth 2.0، وOLD وNEW في عبارات RETURNING، والقيود الزمنية.

هذا ليس Postgres عام 2010. معظم حجج "SQL Server يستطيع وPostgres لا يستطيع" التي أتذكرها انتهت صلاحيتها بصمت.

أين يقف SQL Server الآن

أصبح SQL Server 2025 متاحاً بشكل عام في مؤتمر Ignite في نوفمبر 2025. تقدّمه Microsoft كقاعدة بيانات جاهزة للذكاء الاصطناعي: نوع متجهات أصلي، وفهارس متجهات قائمة على DiskANN، وإدارة النماذج من T-SQL، ونوع JSON أصلي مع الفهرسة، وتعابير نمطية في T-SQL، واستدعاءات REST مدمجة، وبث أحداث التغيير. ويدفع النسخ المتطابق في Fabric البيانات إلى OneLake للتحليلات.

إنه إصدار قوي، موجَّه مباشرة إلى المطورين الذين يعيشون أصلاً في عالم Microsoft.

أين يتفوق Postgres

  • الترخيص. لا رسوم لكل نواة أو لكل إصدار أو Software Assurance عندما تشغّله بنفسك. وفي الخدمة السحابية المُدارة يكون الترخيص مضمَّناً في السعر، لذا تقل أهمية هذا الأمر هناك كثيراً.
  • قابلية النقل. يعمل على Linux وmacOS وWindows والحاويات، وله عرض مُدار في كل سحابة رئيسية. ارتباط أقل بمزوّد واحد.
  • قابلية التوسعة. إضافات مثل PostGIS وpgvector، وأنواع مخصصة، وعدة لغات إجرائية.
  • المعايير والميزات. JSONB، والمصفوفات، وأنواع النطاقات، والفهارس الجزئية وفهارس التعابير، وDDL المعاملاتي (يمكنك التراجع عن تغيير في المخطط).

أين لا يزال SQL Server يتفوق

  • CI/CD والتحكم في المصدر. أقوى نقاط تفوق SQL Server. تعيش قاعدة البيانات في نظام التحكم في المصدر كمشروع، وتولّد الأدوات النشر نيابةً عنك. لا يملك Postgres مكافئاً قياسياً، فتكتب نصوص الترحيل وتصونها يدوياً. التفاصيل في القسم التالي.
  • الأدوات. تشكّل SSMS وSQL Agent وSSIS وSSRS وProfiler صندوق أدوات متكاملاً ومتقناً. أما في Postgres فتجمع صندوقك بنفسك من pgAdmin وcron أو pg_cron وأدوات الأطراف الثالثة.
  • التكامل مع Microsoft. Active Directory وEntra و.NET وPower BI وFabric. إذا كانت شركتك كلها تعمل على Microsoft، فالاحتكاك أقل.
  • ميزات المؤسسات المدمجة. يأتي Columnstore وOLTP في الذاكرة ومجموعات التوفر Always On الناضجة معبّأة ومدعومة كمنتج واحد.
  • جهة مسؤولة واحدة. مزوّد واحد مسؤول عن كل شيء. أما مع Postgres فتختار مزوداً مُداراً أو شركة دعم لهذا الدور.
  • الشرائح. تتيح إصدارات SQL Server ومستويات الخدمة أن يكلّف الحمل الصغير أقل بكثير من شريحة متوسطة عادية. ليس في Postgres مثل هذا التدرج: إنه المحرك نفسه في كل مكان، فتكلفة الطرف الصغير تحددها الاستضافة التي تختارها، لا إصدار مبتدئ رخيص.

Postgres لا يزال يلحق بالركب

محرك التخزين ونواة SQL في Postgres ناضجان جداً. أما الطبقة المحيطة بهما، أي الميزات التي تتوقعها المؤسسات الكبيرة جاهزة، فهي أحدث، وقد أمضى Postgres الإصدارات القليلة الأخيرة في سد فجوات سدّها SQL Server منذ زمن بعيد:

  • الإجراءات المخزنة مع التحكم في المعاملات وصلت في PostgreSQL 11 (2018). أما T-SQL ففيه الإجراءات منذ أيامه الأولى.
  • MERGE لم يصل إلا في PostgreSQL 15 (2022). وهو موجود في SQL Server منذ 2008.
  • الأعمدة المولَّدة الافتراضية جديدة في PostgreSQL 18. وفي SQL Server أعمدة محسوبة منذ عقود.
  • OLD وNEW في RETURNING (PostgreSQL 18) هو ردّ Postgres على عبارة OUTPUT inserted/deleted في T-SQL.
  • القيود الزمنية (PostgreSQL 18) خطوة نحو الجداول الزمنية التي قدّمها SQL Server في 2016.
  • مصادقة OAuth 2.0 (PostgreSQL 18) هي حل تسجيل الدخول الموحد الذي يحصل عليه SQL Server عبر Active Directory وEntra.

كل إصدار يقرّب Postgres من SQL Server، لكن الفجوات المتبقية هي التي تحسم المشاريع الحقيقية، وأكبرها CI/CD. فمن دون طريقة قياسية لتعريف قاعدة البيانات في نظام التحكم في المصدر ونشرها من خط أنابيب، يكلّف كل تغيير نصوص ترحيل مكتوبة يدوياً. وبالنسبة إلى فريق يريد أن تُعرَّف قاعدة البيانات بملفاته المصدرية، فهذا عيب خطير وقد يكون عاملاً حاسماً.

CI/CD والتحكم في المصدر: أكبر مكاسب SQL Server

هذا هو أقوى تفوق لـ SQL Server على Postgres، وأول ما كنت سأزنه.

في SQL Server تكون قاعدة البيانات مشروعاً في نظام التحكم في المصدر. تعيش الجداول والإجراءات والعروض والمشغِّلات كملفات CREATE عادية، وتقارن الأدوات (مشاريع قواعد بيانات SSDT وsqlpackage) هذا المشروع بقاعدة بيانات حية وتولّد النشر نيابةً عنك. أنت تحرّر الحالة المطلوبة، والأداة تستنتج التغيير. ويتكامل مباشرة مع Visual Studio وAzure DevOps وGitHub Actions.

لا يملك Postgres مكافئاً قياسياً. أسلوب العمل السائد هو نصوص الترحيل: لكل تغيير تكتب بيدك نصاً مرقماً ينقل قاعدة البيانات من إصدار إلى التالي، وتحتفظ بها كلها إلى الأبد. يمكن لأدوات مثل Flyway وLiquibase تطبيق هذه النصوص تلقائياً من خط أنابيب، لكن على إنسان أن يكتب كل واحد منها يدوياً قبل الإيداع (commit). في SQL Server تودِع الحالة المطلوبة، ويستنتج خط الأنابيب التغيير وينشره بنفسه. توجد أدوات قائمة على الحالة تقارن الملفات بقاعدة بيانات حية (مثل Atlas وpg-schema-diff)، لكنها أحدث وأقل انتشاراً وليست رسمية. وتحتاج الإجراءات المخزنة فوق ذلك إلى خطوة إعادة بناء خاصة بك.

إذا أردت أن تُعرَّف قاعدة بياناتك بالملفات المصدرية وحدها، ولا تستطيع تحمّل كتابة كل نص ترحيل وصيانته يدوياً، فإن SQL Server هو الخيار الأكثر أماناً.

ما تدفعه وما تشعر به مع ازدياد الاستدعاءات. سعرا Azure SQL، $5 و$15، ثابتان للشريحة. تدفعهما سواء تلقّت قاعدة البيانات استدعاءً واحداً في اليوم أو مليوناً. ما يحدّك هو السعة. حين تحتاج الاستدعاءات إلى أكثر من 5 أو 10 DTU للشريحة، تتباطأ الاستعلامات، وتعالج ذلك بالانتقال إلى شريحة أعلى، لا بالدفع عن كل استدعاء.

يعمل Postgres بالطريقة نفسها من حيث السعر، لكن الإحساس عند الحد مختلف. سعر B1ms كذلك ثابت في الساعة مهما بلغ عدد الاستدعاءات. لكن B1ms خادم "burstable" مصمم لقواعد البيانات الخاملة في معظم الأوقات. وهو في خموله يدّخر أرصدة، كحساب مصرفي، وتستهلكها اللحظات المزدحمة. وإذا بقي مشغولاً مدة طويلة تنفد الأرصدة وقد يتوقف الخادم عن الاستجابة. وتعالج ذلك بالطريقة نفسها، بالانتقال إلى عدد أكبر من vCores، وهو ما تقول Microsoft إنه يستغرق ثوانيَ. إذن مع قاعدتَي البيانات كلتيهما، لا تؤدي زيادة الاستدعاءات إلى رفع الفاتورة. بل تدفعك إلى شريحة أكبر، والشريحة الأكبر هي التي ترفعها.

العرض المجاني والخدمة عديمة الخادم (serverless) استثناء. فهما يحاسبان على الحوسبة التي تستخدمها فعلاً، بالثانية، لذا فإن وتيرة الاستدعاءات مهمة مباشرة: الاستدعاءات المتكررة تُبقي قاعدة البيانات مستيقظة وتستهلك الحصة المجانية.

بالنسبة إلى هذا الحمل، تعتمد الإجابة على عدد ساعات اليوم التي تبقى فيها قاعدة البيانات مستيقظة. إذا كان التطبيق يوقظ قاعدة البيانات بضع دقائق في كل مرة ثم يهدأ، فإن العرض المجاني يغطي ذلك. وإذا نفدت الحصة الشهرية، فإنك تختار بين إيقاف قاعدة البيانات مؤقتاً حتى الشهر التالي ودفع الأسعار القياسية.

لدى Postgres على Azure حدّ أدنى للسعر. يكلّف B1ms نحو $12 شهرياً للحوسبة وحدها، أي نحو $144 سنوياً قبل التخزين والنسخ الاحتياطية، سواء استخدمه أحد أم لا. لم أجد ما يعادل الإيقاف التلقائي في serverless. يمكنك إيقاف خادم مرن، لكن Azure يعيد تشغيله تلقائياً بعد 7 أيام ما لم تشغّله بنفسك قبل ذلك. كما أن الشريحة القابلة للاندفاع (burstable) مخصصة للأحمال التي تبقى خاملة أو دون خط الأساس: إذا ظل المعالج مرتفعاً تنفد الأرصدة وقد يصبح الخادم غير قابل للوصول، وتصف Microsoft هذه الشريحة بأنها مخصصة بالدرجة الأولى للاستخدام غير الإنتاجي.

هناك أمران قد يغيّران الصورة:

  • المشاركة. يمكن لخادم Postgres واحد أن يستضيف قواعد بيانات كثيرة، فإذا كانت كل مشاريعك على خادم واحد تُقسَّم الـ $12. أما العرض المجاني لـ SQL Server فهو لكل قاعدة بيانات.
  • الحمل المستمر. إذا كان التطبيق يصل إلى قاعدة البيانات على مدار الساعة، فإن الحصة المجانية لـ SQL (نحو 28 ساعة من vCore واحد) تنفد سريعاً وستدفع أسعار serverless القياسية. لم أجد سعراً حالياً بالثانية، فسعِّر الخيارين في حاسبة Azure بحملك الحقيقي قبل أن تقرر.

الخلاصة: Postgres ليس أرخص. القول إنه أرخص خرافة شائعة. البرنامج مجاني، لكنك في الخدمة السحابية المُدارة تدفع مقابل الحوسبة والتخزين لا مقابل ترخيص، وترخيص SQL Server مضمَّن في سعره على أي حال. عند 20 جيجابايت يساوي أرخص خيار في SQL Server أداء Postgres أو يتفوق عليه عند كل مستوى استخدام: مجاني حتى نحو ساعتين من الاستيقاظ يومياً، ثم Standard S0 بنحو $180 سنوياً مقابل نحو $190 لـ Postgres. الفارق عند S0 صغير، فاقرأه على أنه تعادل تقريبي في أحسن الأحوال لصالح Postgres، وأنه ليس أرخص بوضوح أبداً. وللاطلاع على العروض المجانية التي تجعل ذلك ممكناً، راجع Hunting Freebies in the Clouds، الذي يقارن عروض قواعد البيانات والحوسبة المجانية من Azure وGoogle وAWS وOracle وCloudflare.

طريقة عملية للحسم

كنت سأختار Postgres عندما:

  • تكون قاعدة البيانات صغيرة وتتألف في معظمها من جداول وعروض لا تتغير ولا تتطور.
  • يكون الترخيص بنداً مؤثراً في التكلفة، أو تكون مضغوطاً بسبب عدد الأنوية.
  • تريد تشغيل قاعدة البيانات نفسها على أي سحابة أو على حاسوب محمول.
  • يعرف فريقك Postgres بالفعل، أو يرغب في تعلمه.

وكنت سأختار SQL Server عندما:

  • يتغير مخطط SQL لديك كثيراً ويكون CI/CD مهماً: تريد تعريف قاعدة البيانات في نظام التحكم في المصدر ونشرها من خط أنابيب من دون نصوص ترحيل مكتوبة يدوياً.
  • سيعيش جزء كبير من منطق أعمالك في الإجراءات المخزنة.
  • تريد SSIS وSSRS وSQL Agent جزءاً من المنصة.
  • تلتزم الشركة بحزمة Microsoft، بما فيها Fabric وPower BI.

إذا كنت مترددا، فزِن CI/CD أولاً.

الحكم

يمكن استخدام Postgres لمشروع صغير جداً باحتياجات أساسية لحفظ البيانات. أما لأي شيء أكبر، فيعتمد الاختيار على المهمة، وعلى القدرات التي تحتاجها حول قاعدة البيانات، وقبل كل شيء على سير عمل CI/CD لديك، وهو المجال الذي يتفوق فيه SQL Server بأوضح صورة. إذا أردت أن تدفع commit فتنشر قاعدة البيانات نفسها بنفسها، فابدأ بـ SQL Server.
