私の短い答えはこうです。データを形づくるロジックはデータベースに置き、アプリケーションコードは本当にデータベースの外にあるものに使いましょう。

これは何十年も続いてきた、ソフトウェア界でも屈指の熱い議論です。一方の陣営はストアドプロシージャをあらゆるデータ変換ロジックの自然な置き場所とみなし、もう一方はそれを完全に禁止します。開発者フォーラムには、ロジックをストアドプロシージャに入れたというだけでコードレビューを却下されたり、仕事を批判されたりした人たちの不満があふれています。

AI を活用した開発は、この議論の空気を変えました。AI アシスタントはどちらかの陣営に加わるのではなく、ケースごとに理由を見て判断します。今では AI 自身がストアドプロシージャを提案し、その理由を説明することがとても多いのは印象的です。セット指向の処理、アトミックな変更、明確なセキュリティ境界といった理由です。この記事の残りは、そのケースごとの考え方です。

ストアドプロシージャが真価を発揮する場面

私は SQL もアプリケーションコードも数多く書いてレビューしており、どちらの側の教条にも与しません。ロジックが本当にデータそのものについての記述であり、その表現や可視化についてではない場合、ストアドプロシージャは適切な道具です。

  • セット指向の処理。100 万行を 1 回の MERGE で移すほうが、ネットワーク越しに引き出して C# や Python でループし、また書き戻すよりはるかに優れています。
  • ネットワークの往復がない。アプリケーションコード内のビジネスロジックは、必要な行をすべてデータベースから取り出し、結果をすべて保存のために送り返さなければなりません。これでトラフィックは倍になり、各ステップに遅延が加わり、呼び出しのたびに積み重なります。プロシージャは同じ場所で読み、計算し、書き込み、ネットワークを通るのは最終結果だけです。隠れたコストはサーバー側にあります。小さな呼び出しが何千回もあれば同時接続も何千本になり、アクティブな要求はそれぞれワーカースレッドを占有します。ワーカー数の上限はコア数に結びついているため、CPU がまだ余っているように見えるうちにスレッドが尽きます。唯一の解決策は接続を保持するためだけに vCore を買い足すことで、結局ロジックをデータベース内に置いた場合よりもデータベースの請求額が高くなります。
  • 複数テーブルにまたがるアトミックな変更。全体として成功するか失敗するかのどちらかでなければならないトランザクションは、データのある場所で行うのがいちばん安全です。
  • デバッグ。プロシージャを実データに対して実行し、ステップごとに追い、途中経過のすべてを単純な SELECT で確認できます。バグの再現は、同じパラメータで再実行するだけです。同じルールをアプリのコントローラー、サービス、ORM、ログをまたいで追いかけるのは、はるかに骨の折れる作業です。
  • バージョン管理とデプロイ。Microsoft の SQL Server データベースプロジェクトが何年も前にこの問題を解決しました。プロシージャは他のコードと同じように Git に置かれ、GitHub Actions のパイプラインがプロジェクトと対象データベースを比較して、変わった部分だけを適用します。プロシージャのデプロイは、アプリのリリースより小さく、ストレスも少ないことがよくあります。
  • データの整合性。不変条件を強制する制約、トリガー、プロシージャは、誰も書いたことを覚えていないクライアントも含め、あらゆるクライアントからデータを守ります。
  • 権限。プロシージャに EXECUTE を付与しつつテーブルへの直接アクセスを拒否するのは、明快で監査しやすいセキュリティ境界です。
  • バッチと ETL ジョブ。データの近くでファイルを読み込み、重複を除き、突き合わせるのは、速くて簡単です。

つらくなる場面

ストアドプロシージャにもトレードオフがないわけではありません。実際のものは次のとおりです。

  • スケールの偏り。アプリケーションサーバーは安く増やせますが、データベースの CPU は増やすのにいちばんお金がかかります。データのすぐ隣にある必要のない CPU 負荷の高い計算は、コードに置くほうが向いています。
  • 移植性が失われる。方言に依存した手続き型コードは事業を 1 つのベンダーに縛り、移行は書き直しになります。
  • 知識が属人化する。手続き型 SQL を流暢に読める開発者は少ないため、ルールを理解しているのは 1、2 人になりがちです。長年の「ロジックをデータベースに置くな」という助言のせいで、本当の SQL スペシャリストは本当に希少になりました。そうした人材を抱える会社は、彼らを重要人材として扱い、手放さないよう努力すべきです。

AI を活用した開発が変えること

AI コーディングツールは、データベースコードに対する昔ながらの反対理由の大半を取り除きました。

AI アシスタントは、プロシージャのリファクタリングやスキーマ全体にわたる依存関係の追跡、SQL のレビューを、アプリケーションコードと同じように軽々とこなします。AI コーディングアシスタントがすでにその作業をしてくれるなら、専用の SQL コード解析ツールを買う意味はほとんどありません。

AI はセット指向の SQL を書いたりチューニングしたりするのもとても得意なので、データベースに置くべきデータ集約型の作業を正しく仕上げるコストは、以前より下がっています。

一つだけ注意が残ります。アシスタントには実際のスキーマ、トリガー、権限、データ量を与えてください。単独で読んだプロシージャは、正しく見えても本番で失敗することがあるからです。

実例:ロジックはデータベースに、コストは低く

ロジックをデータベースに置くことは、ページを表示するたびにデータベースにアクセスするという意味ではありません。stas.club の Crypto Jobs ページが、その両立のしかたを示しています。

求人情報は Azure SQL データベースにあり、そこにあるプロシージャがどの求人が暗号資産関連かを判定して一覧を整えます。これはデータのロジックなので、データベースに残ります。しかし、誰もがいつでも読み込める公開ページは、データベースを起こし続けることになります。サーバーレスの Azure SQL データベースは、起こすのにお金がかかり、ページが数分止まることもあります。

そこで、このページはデータベースに一切触れません。

  1. Google Cloud 上の毎日のスケジュールジョブが、サイトの Web API を呼び出します。ジョブ自体にビジネスロジックはなく、仕事をするのは API とその裏にあるプロシージャなので、同じ更新を手動でも実行できます。
  2. API がプロシージャを実行し、完成した一覧を返します。
  3. ジョブはその一覧を JSON ファイルとして、無料枠の Cloudflare R2 バケットに書き込みます。
  4. 誰かがページを開くと、サイトは R2 から用意済みのファイルを読み込みます。データベースはまったく関与しません。

その結果、データベースの呼び出しは訪問者ごとではなく 1 日 1 回になります。ルールは今も 1 か所にあり、ページは一瞬で表示され、データベースは 1 日の残りを眠って過ごせます。

判断のための経験則

そのロジックが何についてのものかを問います。データをどう形づくり、動かし、守るかを記述しているなら、データベースに属します。ライブの外部データ、ネットワーク呼び出し、ユーザーインターフェースなど、データベースの外にあるものを必要とするなら、コードに属します。

ロジック適した置き場所理由
一括読み込み、マージ、重複排除ストアドプロシージャセット指向で、データの隣にある
参照整合性と一意性のルール制約すべてのクライアントに強制される
行レベルのアクセス制御データベースの権限強制する場所が 1 か所
価格設定、割引、スコアリングストアドプロシージャセット指向で、すべての利用側に同じ答えを返し、確認しやすい
ワークフローと承認の状態ストアドプロシージャ許可される遷移を 1 か所で強制し、監査できる
ライブデータが必要なルール(市場価格、API フィード)アプリケーションコードデータがデータベースの外にある
外部サービスの呼び出しアプリケーションコードデータベースはネットワーク呼び出しをすべきではない

結論

ストアドプロシージャはビジネスロジックの置き場所として、悪くないどころか良い場所です。スコアリング、価格設定、ワークフローの状態、整合性のように、データについてのルールはデータの隣に置くべきです。そこならセット指向で動き、すべての利用側に同じ答えを返し、確認もしやすくなります。アプリケーションコードは、ライブの外部データ、ネットワーク呼び出し、ユーザーインターフェースなど、本当にデータベースの外にあるものに使ってください。

それでも同意しないエンジニアはいるでしょうし、少数には正当な理由があります。SQL のスキルが乏しいチームや、すでに計算リソースの限界に達しているデータベースなどです。それ以外のすべての人は、ルールが何についてのものかを問い、そのデータがある場所に置いてください。この選択は、習慣ではなく意図を持って行いましょう。
