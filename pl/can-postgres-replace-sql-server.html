Ten wpis dotyczy wyboru bazy danych dla nowego projektu, zaczynanego od zera. Krótka odpowiedź: jako silnik bazy danych Postgres jest w porządku. Jako działająca platforma zależy od Twojego procesu CI/CD i od narzędzi, których potrzebujesz wokół bazy danych.

Tak o tym myślę po trzech dekadach budowania oprogramowania po obu stronach tego płotu.

Pytanie za pytaniem

„Od jakiej bazy danych zacząć?” to tak naprawdę trzy pytania:

  • Jakie jest zadanie? Nikt nie płaci za SQL Server tylko po to, by przechowywać dane. Używamy go do pracy z danymi: procedury składowane, przekształcenia zbiorowe, zaplanowane zadania, ETL i raportowanie, z logiką biznesową działającą tuż obok danych. Najpierw zdefiniuj to obciążenie, a potem zapytaj, czy Postgres da sobie z nim radę.
  • Czy ma możliwości, których potrzebuję? Funkcje, od których moje obciążenie zależy dziś: procedury, harmonogramowanie, ETL, raportowanie, bezpieczeństwo, narzędzia. Nikt nie wybiera bazy danych po to, by móc ją później opuścić, więc test brzmi: czy robi to, czego potrzebuję teraz.
  • Ile to kosztuje? Wynika to z dwóch pierwszych odpowiedzi, bo to zadanie wyznacza wzór. Stałe, ciężkie obciążenie wycenia się według liczby rdzeni CPU, które utrzymujesz włączone. Nieregularne wycenia się według tego, jak często jest wywoływane i jak ciężkie jest każde zadanie, i tam mogą wygrać poziomy płatne za użycie lub serverless. Licencje, hosting i ludzie dochodzą do tego z góry.

To zależy od zadania. Przechowywanie i odpytywanie danych: łatwe. Praca z danymi wewnątrz bazy: Postgres dobrze radzi sobie z SQL i kodem proceduralnym, ale nie z platformą wokół niego (harmonogramowanie, ETL, raportowanie). Drugie pytanie pokazuje, po której stronie leży Twoje obciążenie. Trzecie, koszt, wynika z dwóch pierwszych: płacisz albo za stale włączony procesor, albo za to, jak często i jak ciężko wywołujesz bazę danych.

Gdzie dziś jest Postgres

PostgreSQL 18 ukazał się 25 września 2025 roku. Najważniejszą nowością jest nowy asynchroniczny podsystem I/O, który według projektu pokazał nawet 3-krotnie szybszy odczyt z magazynu. Zachowuje też statystyki planera przy aktualizacjach między głównymi wersjami, co usuwa jedno z bardziej uciążliwych spowolnień po aktualizacji. Nowości dla programistów to m.in. wirtualne kolumny generowane, uuidv7(), uwierzytelnianie OAuth 2.0, OLD i NEW w klauzulach RETURNING oraz ograniczenia czasowe.

To nie jest Postgres z 2010 roku. Większość argumentów „SQL Server to potrafi, Postgres nie”, które pamiętam, po cichu wygasła.

Gdzie dziś jest SQL Server

SQL Server 2025 stał się ogólnie dostępny na konferencji Ignite w listopadzie 2025 roku. Microsoft pozycjonuje go jako bazę gotową na AI: natywny typ wektorowy, indeksy wektorowe oparte na DiskANN, zarządzanie modelami z poziomu T-SQL, natywny typ JSON z indeksowaniem, wyrażenia regularne w T-SQL, wbudowane wywołania REST i strumieniowanie zdarzeń zmian. Mirroring w Fabric przesyła dane do OneLake na potrzeby analityki.

To mocne wydanie, wymierzone prosto w programistów, którzy już żyją w świecie Microsoftu.

Gdzie wygrywa Postgres

  • Licencjonowanie. Brak opłat za rdzeń, za edycję czy za Software Assurance, gdy uruchamiasz go samodzielnie. W zarządzanej usłudze chmurowej licencja jest wliczona w cenę, więc tam ma to znacznie mniejsze znaczenie.
  • Przenośność. Linux, macOS, Windows, kontenery i zarządzana oferta w każdej dużej chmurze. Mniejsze uzależnienie od dostawcy.
  • Rozszerzalność. Rozszerzenia takie jak PostGIS i pgvector, własne typy i kilka języków proceduralnych.
  • Standardy i funkcje. JSONB, tablice, typy zakresowe, indeksy częściowe i wyrażeniowe oraz transakcyjny DDL (zmianę schematu można wycofać).

Gdzie SQL Server nadal wygrywa

  • CI/CD i kontrola wersji. Najsilniejsza przewaga SQL Server. Baza danych żyje w kontroli wersji jako projekt, a narzędzia generują wdrożenie za Ciebie. Postgres nie ma standardowego odpowiednika, więc skrypty migracji piszesz i utrzymujesz ręcznie. Szczegóły w następnej sekcji.
  • Narzędzia. SSMS, SQL Agent, SSIS, SSRS i Profiler tworzą ściśle zintegrowany, dopracowany zestaw. W Postgresie składasz własny z pgAdmin, crona lub pg_cron oraz narzędzi firm trzecich.
  • Integracja z Microsoftem. Active Directory i Entra, .NET, Power BI, Fabric. Jeśli cała Twoja firma działa na Microsofcie, tarcie jest mniejsze.
  • Wbudowane funkcje klasy enterprise. Columnstore, OLTP w pamięci i dojrzałe grupy dostępności Always On są pakowane i wspierane jako jeden produkt.
  • Jeden odpowiedzialny. Za wszystko odpowiada jeden dostawca. W przypadku Postgresa do tej roli wybierasz zarządzanego dostawcę lub firmę wsparcia.
  • Poziomy. Edycje i poziomy usług SQL Server sprawiają, że małe obciążenie może kosztować znacznie mniej niż przeciętny średni poziom. Postgres nie ma takiego stopniowania: to wszędzie ten sam silnik, więc koszt na małym końcu wyznacza wybrany hosting, a nie tania edycja startowa.

Postgres wciąż nadrabia

Silnik składowania i rdzeń SQL Postgresa są bardzo dojrzałe. Warstwa wokół nich, czyli funkcje, których duże przedsiębiorstwa oczekują od ręki, jest młodsza, a Postgres przez kilka ostatnich wydań zamykał luki, które SQL Server zamknął dawno temu:

  • Procedury składowane z kontrolą transakcji pojawiły się w PostgreSQL 11 (2018). T-SQL ma procedury od początku.
  • MERGE pojawił się dopiero w PostgreSQL 15 (2022). SQL Server ma go od 2008 roku.
  • Wirtualne kolumny generowane są nowością w PostgreSQL 18. SQL Server ma kolumny obliczeniowe od dziesięcioleci.
  • OLD i NEW w RETURNING (PostgreSQL 18) to odpowiedź Postgresa na klauzulę OUTPUT inserted/deleted w T-SQL.
  • Ograniczenia czasowe (PostgreSQL 18) zmierzają w stronę tabel temporalnych, które SQL Server wprowadził w 2016 roku.
  • Uwierzytelnianie OAuth 2.0 (PostgreSQL 18) to rozwiązanie jednokrotnego logowania, które SQL Server zyskuje dzięki Active Directory i Entra.

Każde wydanie przybliża Postgresa do SQL Servera, ale pozostałe luki rozstrzygają realne projekty, a największą z nich jest CI/CD. Bez standardowego sposobu zdefiniowania bazy danych w kontroli wersji i wdrażania jej z pipeline'u każda zmiana kosztuje ręcznie pisane skrypty migracji. Dla zespołu, który chce, by baza danych była zdefiniowana przez pliki źródłowe, to poważna wada i może być czynnikiem przesądzającym.

CI/CD i kontrola wersji: największa przewaga SQL Server

To najsilniejsza przewaga SQL Server nad Postgresem i pierwsza rzecz, którą bym rozważył.

W SQL Server baza danych jest projektem w kontroli wersji. Tabele, procedury, widoki i wyzwalacze są zwykłymi plikami CREATE, a narzędzia (projekty baz danych SSDT, sqlpackage) porównują ten projekt z działającą bazą i generują wdrożenie za Ciebie. Edytujesz stan docelowy, a narzędzie ustala zmianę. Wpina się bezpośrednio w Visual Studio, Azure DevOps i GitHub Actions.

Postgres nie ma standardowego odpowiednika. Główny sposób pracy to skrypty migracji: przy każdej zmianie ręcznie piszesz numerowany skrypt, który przenosi bazę z jednej wersji do następnej, i przechowujesz je wszystkie na zawsze. Narzędzia takie jak Flyway i Liquibase mogą stosować te skrypty automatycznie z pipeline'u, ale człowiek wciąż musi napisać każdy z nich ręcznie przed commitem. W SQL Server commitujesz stan docelowy, a pipeline sam ustala i wdraża zmianę. Narzędzia oparte na stanie, które porównują pliki z działającą bazą, istnieją (na przykład Atlas i pg-schema-diff), ale są młodsze, mniej rozpowszechnione i nie pochodzą od głównego dostawcy. Procedury składowane wymagają dodatkowo własnego kroku odbudowy.

Jeśli chcesz, by Twoja baza danych była zdefiniowana wyłącznie przez pliki źródłowe i nie możesz sobie pozwolić na ręczne pisanie i utrzymywanie każdego skryptu migracji, SQL Server jest bezpieczniejszym wyborem.

Weźmy średniej wielkości bazę danych: 20 GB, używaną zrywami, a nie przez całą dobę. Obie opcje działałyby w Azure. Ile bym zapłacił?

Te ceny są przybliżone. Wziąłem je z zestawień firm trzecich, a cena magazynu Postgresa to moje własne oszacowanie (około $0,115 za GiB miesięcznie). Zanim się zdecydujesz, sprawdź kalkulator cen Azure.

Co płacisz i co czujesz, gdy wywołań przybywa. Ceny Azure SQL $5 i $15 są stałe dla danego poziomu. Płacisz je niezależnie od tego, czy baza dostaje jedno wywołanie dziennie, czy milion. Ogranicza Cię przepustowość. Gdy wywołania wymagają więcej niż 5 lub 10 DTU poziomu, zapytania zwalniają, a rozwiązujesz to przejściem na wyższy poziom, a nie płaceniem za wywołanie.

Postgres działa pod względem ceny tak samo, ale na granicy odczuwa się to inaczej. Cena B1ms jest również stała za godzinę, bez względu na to, ile wywołań nadejdzie. Ale B1ms to serwer „burstable”, zbudowany dla baz danych, które przez większość czasu pozostają bezczynne. Gdy jest bezczynny, odkłada kredyty jak konto bankowe, a intensywne chwile je zużywają. Jeśli zbyt długo pozostaje zajęty, kredyty się kończą i serwer może przestać odpowiadać. Naprawiasz to tak samo, przechodząc na więcej vCore, co według Microsoftu zajmuje sekundy. Czyli w obu bazach więcej wywołań nie podnosi rachunku. Wpychają Cię na większy poziom, a to większy poziom go podnosi.

Oferta bezpłatna i serverless są wyjątkiem. Rozliczają faktycznie użytą moc obliczeniową, za sekundę, więc częstotliwość wywołań ma bezpośrednie znaczenie: częste wywołania utrzymują bazę w stanie aktywnym i zużywają bezpłatny limit.

W tym obciążeniu odpowiedź zależy od tego, ile godzin dziennie baza jest aktywna. Jeśli aplikacja budzi bazę na kilka minut, a potem cichnie, oferta bezpłatna to pokrywa. Jeśli miesięczny limit się wyczerpie, wybierasz między wstrzymaniem bazy do następnego miesiąca a płaceniem stawek standardowych.

Postgres w Azure ma dolną granicę ceny. B1ms kosztuje około $12 miesięcznie samej mocy obliczeniowej, czyli około $144 rocznie przed magazynem i kopiami zapasowymi, niezależnie od tego, czy ktoś z niego korzysta. Nie znalazłem odpowiednika automatycznego wstrzymywania w serverless. Serwer elastyczny można zatrzymać, ale Azure uruchamia go ponownie automatycznie po 7 dniach, jeśli wcześniej sam go nie uruchomisz. Poziom burstable jest też przeznaczony dla obciążeń, które pozostają bezczynne lub poniżej poziomu bazowego: jeśli CPU pozostaje wysokie, kredyty się kończą i serwer może stać się nieosiągalny, a Microsoft opisuje ten poziom głównie jako przeznaczony do środowisk nieprodukcyjnych.

Dwie rzeczy mogą zmienić obraz:

  • Współdzielenie. Jeden serwer Postgres może hostować wiele baz danych, więc jeśli wszystkie Twoje projekty są na jednym serwerze, te $12 się dzieli. Oferta bezpłatna SQL Server dotyczy pojedynczej bazy.
  • Stałe obciążenie. Jeśli aplikacja odwołuje się do bazy przez całą dobę, bezpłatny limit SQL (około 28 godzin jednego vCore) szybko się kończy i płacisz standardowe stawki serverless. Nie znalazłem aktualnej stawki za sekundę, więc przed decyzją wyceń obie opcje w kalkulatorze Azure przy swoim rzeczywistym obciążeniu.

Podsumowanie: Postgres nie jest tańszy. To, że jest tańszy, to powszechny mit. Oprogramowanie jest bezpłatne, ale w zarządzanej usłudze chmurowej płacisz za moc obliczeniową i magazyn, a nie za licencję, a licencja SQL Server jest i tak wliczona w jego cenę. Przy 20 GB najtańsza opcja SQL Server dorównuje Postgresowi lub go pokonuje na każdym poziomie użycia: bezpłatnie do około 2 godzin aktywności dziennie, potem Standard S0 za około $180 rocznie wobec około $190 dla Postgresa. Różnica przy S0 jest niewielka, więc odczytaj ją jako w najlepszym razie mniej więcej remis dla Postgresa, a nigdy wyraźnie taniej. O bezpłatnych ofertach, które to umożliwiają, przeczytasz w Hunting Freebies in the Clouds, gdzie porównuję bezpłatne oferty baz danych i mocy obliczeniowej od Azure, Google, AWS, Oracle i Cloudflare.

Praktyczny sposób podjęcia decyzji

Wybrałbym Postgresa, gdy:

  • Baza danych jest mała i składa się głównie z tabel i widoków, które nigdy się nie zmieniają ani nie ewoluują.
  • Licencje są znaczącą pozycją kosztów albo jesteś ściskany liczbą rdzeni.
  • Chcesz uruchamiać tę samą bazę danych w dowolnej chmurze lub na laptopie.
  • Twój zespół już zna Postgresa albo chce go poznać.

Wybrałbym SQL Server, gdy:

  • Twój schemat SQL często się zmienia, a CI/CD jest ważne: chcesz, by baza danych była zdefiniowana w kontroli wersji i wdrażana z pipeline'u bez ręcznie pisanych skryptów migracji.
  • Duża część Twojej logiki biznesowej będzie żyć w procedurach składowanych.
  • Chcesz mieć SSIS, SSRS i SQL Agent jako część platformy.
  • Firma jest związana ze stosem Microsoftu, w tym z Fabric i Power BI.

Jeśli się wahasz, najpierw rozważ CI/CD.

Werdykt

Postgresa można używać w maleńkim projekcie o podstawowych potrzebach trwałego przechowywania danych. W przypadku czegokolwiek większego wybór zależy od zadania, od możliwości, których potrzebujesz wokół bazy danych, a przede wszystkim od Twojego procesu CI/CD, w którym SQL Server wygrywa najwyraźniej. Jeśli chcesz wypchnąć commit i mieć bazę danych wdrażającą się samodzielnie, zacznij od SQL Server.
