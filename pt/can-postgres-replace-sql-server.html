Este artigo trata de escolher um banco de dados para um projeto novo, começando do zero. Resposta curta: como motor de banco de dados, o Postgres serve bem. Como plataforma de trabalho, depende do seu fluxo de CI/CD e das ferramentas de que você precisa em volta do banco de dados.

É assim que penso depois de três décadas construindo software dos dois lados desta cerca.

A pergunta por trás da pergunta

"Com qual banco de dados devo começar?" são, na verdade, três perguntas:

  • Qual é o trabalho? Ninguém paga pelo SQL Server só para armazenar dados. Nós o usamos para trabalhar com dados: procedimentos armazenados, transformações baseadas em conjuntos, tarefas agendadas, ETL e relatórios, com a lógica de negócio rodando ao lado dos dados. Defina primeiro essa carga de trabalho e depois pergunte se o Postgres dá conta dela.
  • Ele tem as capacidades de que preciso? Os recursos dos quais minha carga de trabalho depende hoje: procedimentos, agendamento, ETL, relatórios, segurança, ferramentas. Ninguém escolhe um banco de dados para poder sair dele depois, então o teste é se ele faz o que preciso agora.
  • Quanto custa? Isso decorre das duas primeiras respostas, porque o trabalho decide a fórmula. Uma carga constante e pesada é precificada pelo número de núcleos de CPU que você mantém ligados. Uma carga irregular é precificada pela frequência das chamadas e pelo peso de cada tarefa, e aí os níveis de pagamento por uso ou serverless podem ganhar. Licenciamento, hospedagem e pessoas vêm por cima disso.

Depende do trabalho. Armazenar e consultar dados: fácil. Trabalhar com os dados dentro do banco: o Postgres lida bem com SQL e código procedural, mas não com a plataforma em volta (agendamento, ETL, relatórios). A segunda pergunta mostra de que lado está a sua carga de trabalho. A terceira, o custo, decorre das duas primeiras: você paga por uma CPU sempre ligada ou pela frequência e pelo peso das chamadas ao banco de dados.

Onde o Postgres está hoje

O PostgreSQL 18 foi lançado em 25 de setembro de 2025. O destaque é um novo subsistema de E/S assíncrona, que segundo o projeto mostrou leituras até 3 vezes mais rápidas a partir do armazenamento. Ele também mantém as estatísticas do planejador entre atualizações de versão principal, o que elimina uma das lentidões mais incômodas pós-atualização. Entre as novidades para desenvolvedores estão colunas geradas virtuais, uuidv7(), autenticação OAuth 2.0, OLD e NEW em cláusulas RETURNING e restrições temporais.

Este não é o Postgres de 2010. A maioria dos argumentos de "o SQL Server faz, o Postgres não" de que me lembro expirou silenciosamente.

Onde o SQL Server está hoje

O SQL Server 2025 chegou à disponibilidade geral na Ignite, em novembro de 2025. A Microsoft o posiciona como um banco de dados pronto para IA: tipo vetorial nativo, índices vetoriais baseados em DiskANN, gerenciamento de modelos a partir do T-SQL, tipo JSON nativo com indexação, expressões regulares no T-SQL, chamadas REST integradas e streaming de eventos de alteração. O espelhamento do Fabric envia dados para o OneLake para análise.

É um lançamento forte, voltado diretamente para desenvolvedores que já vivem no mundo Microsoft.

Onde o Postgres ganha

  • Licenciamento. Sem taxas por núcleo, por edição ou de Software Assurance quando você mesmo o executa. Em um serviço de nuvem gerenciado, a licença está embutida no preço, então isso importa muito menos ali.
  • Portabilidade. Linux, macOS, Windows, contêineres e uma oferta gerenciada em todas as grandes nuvens. Menos dependência de fornecedor.
  • Extensibilidade. Extensões como PostGIS e pgvector, tipos personalizados e várias linguagens procedurais.
  • Padrões e recursos. JSONB, arrays, tipos de intervalo, índices parciais e de expressão, e DDL transacional (você pode reverter uma alteração de esquema).

Onde o SQL Server ainda ganha

  • CI/CD e controle de versão. A maior vitória do SQL Server. O banco de dados vive no controle de versão como um projeto, e as ferramentas geram a implantação para você. O Postgres não tem equivalente padrão, então você escreve e mantém scripts de migração à mão. Detalhes na seção abaixo.
  • Ferramentas. SSMS, SQL Agent, SSIS, SSRS e Profiler formam um conjunto de ferramentas polido e fortemente integrado. No Postgres, você monta o seu a partir do pgAdmin, cron ou pg_cron e ferramentas de terceiros.
  • Integração com a Microsoft. Active Directory e Entra, .NET, Power BI, Fabric. Se toda a sua empresa roda em Microsoft, há menos atrito.
  • Recursos empresariais integrados. Columnstore, OLTP na memória e grupos de disponibilidade Always On maduros são empacotados e suportados como um único produto.
  • Um único responsável. Um único fornecedor responde por tudo. Com o Postgres, você escolhe um provedor gerenciado ou uma empresa de suporte para esse papel.
  • Níveis. As edições e os níveis de serviço do SQL Server permitem que uma carga pequena custe muito menos que um nível intermediário médio. O Postgres não tem esse gradiente: é o mesmo motor em todo lugar, então o custo na ponta pequena é definido pela hospedagem que você escolhe, não por uma edição de entrada barata.

O Postgres ainda está alcançando

O motor de armazenamento e o núcleo SQL do Postgres são muito maduros. A camada em volta deles, os recursos que grandes empresas esperam já na caixa, é mais jovem, e o Postgres passou os últimos lançamentos fechando lacunas que o SQL Server fechou há muito tempo:

  • Procedimentos armazenados com controle de transação chegaram no PostgreSQL 11 (2018). O T-SQL tem procedimentos desde os seus primeiros dias.
  • MERGE só chegou no PostgreSQL 15 (2022). O SQL Server o tem desde 2008.
  • Colunas geradas virtuais são novidade no PostgreSQL 18. O SQL Server tem colunas computadas há décadas.
  • OLD e NEW em RETURNING (PostgreSQL 18) é a resposta do Postgres à cláusula OUTPUT inserted/deleted do T-SQL.
  • Restrições temporais (PostgreSQL 18) caminham em direção às tabelas temporais que o SQL Server introduziu em 2016.
  • Autenticação OAuth 2.0 (PostgreSQL 18) é a solução de login único que o SQL Server obtém por meio do Active Directory e do Entra.

Cada lançamento aproxima o Postgres do SQL Server, mas as lacunas que restam decidem projetos reais, e a maior é o CI/CD. Sem uma forma padrão de definir o banco de dados no controle de versão e implantá-lo a partir de um pipeline, cada mudança custa scripts de migração escritos à mão. Para uma equipe que quer o banco de dados definido pelos seus arquivos-fonte, isso é uma desvantagem séria e pode ser decisiva.

CI/CD e controle de versão: a maior vitória do SQL Server

Esta é a vitória mais forte do SQL Server sobre o Postgres, e a primeira coisa que eu pesaria.

No SQL Server, o banco de dados é um projeto no controle de versão. Tabelas, procedimentos, views e triggers vivem como simples arquivos CREATE, e as ferramentas (projetos de banco de dados SSDT, sqlpackage) comparam esse projeto com um banco de dados ativo e geram a implantação para você. Você edita o estado desejado e a ferramenta descobre a mudança. Ele se integra diretamente ao Visual Studio, ao Azure DevOps e ao GitHub Actions.

O Postgres não tem equivalente padrão. O fluxo comum são scripts de migração: para cada mudança, você escreve à mão um script numerado que leva o banco de dados de uma versão para a seguinte, e guarda todos para sempre. Ferramentas como Flyway e Liquibase podem aplicar esses scripts automaticamente a partir de um pipeline, mas um humano ainda precisa escrever cada um deles à mão antes do commit. No SQL Server, você faz commit do estado desejado e o pipeline descobre e implanta a mudança sozinho. Existem ferramentas baseadas em estado que comparam arquivos com um banco ativo (Atlas e pg-schema-diff, por exemplo), mas são mais jovens, menos usadas e não são de primeira mão. Procedimentos armazenados precisam ainda do seu próprio passo de reconstrução.

Se você quer o seu banco de dados definido apenas por arquivos-fonte e não pode se dar ao luxo de escrever e manter à mão cada script de migração, o SQL Server é a escolha mais segura.

Comparação de custos: um banco de dados de porte médio

Tome um banco de dados de porte médio: 20 GB, usado em rajadas em vez de o dia todo. As duas opções rodariam no Azure. Quanto eu pagaria?

Esses preços são aproximados. Eu os tirei de resumos de terceiros, e o preço de armazenamento do Postgres é uma estimativa minha (cerca de $0,115 por GiB-mês). Confira a calculadora de preços do Azure antes de se comprometer.

O que você paga, e o que sente, à medida que as chamadas aumentam. Os preços de $5 e $15 do Azure SQL são fixos para o nível. Você os paga quer o banco receba uma chamada por dia ou um milhão. O que limita você é a capacidade. Quando as chamadas precisam de mais que os 5 ou 10 DTUs do nível, as consultas ficam lentas, e você resolve isso subindo para um nível maior, não pagando por chamada.

O Postgres funciona do mesmo jeito no preço, com uma sensação diferente no limite. O preço do B1ms também é fixo por hora, não importa quantas chamadas cheguem. Mas o B1ms é um servidor "burstable", feito para bancos de dados que ficam ociosos na maior parte do tempo. Enquanto está ocioso, ele acumula créditos, como uma conta bancária, e os momentos de movimento os gastam. Se ficar ocupado por muito tempo, os créditos acabam e o servidor pode parar de responder. Você resolve do mesmo modo, subindo para mais vCores, o que, segundo a Microsoft, leva segundos. Então, com os dois bancos de dados, mais chamadas não aumentam a conta. Elas empurram você para um nível maior, e o nível maior é que a aumenta.

A oferta gratuita e o serverless são a exceção. Eles cobram pela computação que você realmente usa, por segundo, então a frequência das chamadas importa diretamente: chamadas frequentes mantêm o banco acordado e consomem a cota gratuita.

Para esta carga de trabalho, a resposta depende de quantas horas por dia o banco fica acordado. Se a aplicação acorda o banco por alguns minutos de cada vez e depois silencia, a oferta gratuita cobre. Se a cota mensal acabar, você escolhe entre pausar o banco até o mês seguinte e pagar as tarifas padrão.

O Postgres no Azure tem um piso de preço. O B1ms custa cerca de $12 por mês só de computação, aproximadamente $144 por ano antes do armazenamento e dos backups, quer alguém o use ou não. Não encontrei um equivalente da pausa automática do serverless. Você pode parar um servidor flexível, mas o Azure o inicia de novo automaticamente após 7 dias, a menos que você o inicie antes. O nível burstable também é pensado para cargas que ficam ociosas ou abaixo da linha de base: se a CPU permanece alta, os créditos acabam e o servidor pode ficar inacessível, e a Microsoft descreve o nível como destinado principalmente a ambientes que não são de produção.

Duas coisas podem mudar o quadro:

  • Compartilhamento. Um servidor Postgres pode hospedar muitos bancos de dados, então, se todos os seus projetos ficam em um único servidor, os $12 são divididos. A oferta gratuita do SQL Server é por banco de dados.
  • Carga constante. Se a aplicação acessa o banco o dia inteiro, a cota gratuita do SQL (cerca de 28 horas de um vCore) acaba rápido e você pagaria as tarifas serverless padrão. Não encontrei uma tarifa atual por segundo, então precifique as duas opções na calculadora do Azure com a sua carga real antes de decidir.

Conclusão: o Postgres não é mais barato. Dizer que é mais barato é um mito comum. O software é gratuito, mas em um serviço de nuvem gerenciado você paga por computação e armazenamento, não por licença, e a licença do SQL Server está embutida no preço de qualquer forma. Com 20 GB, a opção mais barata do SQL Server iguala ou supera o Postgres em todos os níveis de uso: gratuita até cerca de 2 horas acordado por dia, depois o Standard S0 por cerca de $180 por ano contra cerca de $190 do Postgres. A diferença no S0 é pequena, então leia-a como, no melhor caso, um empate para o Postgres, e nunca claramente mais barato. Para as ofertas gratuitas que tornam isso possível, veja Hunting Freebies in the Clouds, que compara as ofertas gratuitas de banco de dados e computação do Azure, Google, AWS, Oracle e Cloudflare.

Um jeito prático de decidir

Eu escolheria o Postgres quando:

  • O banco de dados é pequeno e composto principalmente de tabelas e views que nunca mudam nem evoluem.
  • O licenciamento é um item de custo relevante, ou você está sendo pressionado pelos núcleos.
  • Você quer rodar o mesmo banco de dados em qualquer nuvem ou em um notebook.
  • Sua equipe já conhece o Postgres, ou quer conhecer.

Eu escolheria o SQL Server quando:

  • Seu esquema SQL muda com frequência e o CI/CD é importante: você quer o banco de dados definido no controle de versão e implantado a partir de um pipeline sem scripts de migração escritos à mão.
  • Boa parte da sua lógica de negócio vai viver em procedimentos armazenados.
  • Você quer SSIS, SSRS e SQL Agent como parte da plataforma.
  • A empresa está comprometida com a stack da Microsoft, incluindo Fabric e Power BI.

Se você está em dúvida, pese primeiro o CI/CD.

Veredicto

O Postgres pode ser usado em um projeto minúsculo, com necessidades básicas de persistência de dados. Para qualquer coisa maior, a escolha depende do trabalho, das capacidades de que você precisa em volta do banco de dados e, acima de tudo, do seu fluxo de CI/CD, que é onde o SQL Server ganha com mais clareza. Se você quer dar push em um commit e ver o banco de dados se implantar sozinho, comece com o SQL Server.
