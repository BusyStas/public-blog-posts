คำตอบสั้น ๆ ของผมคือ ให้วางตรรกะที่กำหนดรูปร่างของข้อมูลไว้ในฐานข้อมูล และเก็บโค้ดแอปพลิเคชันไว้สำหรับสิ่งที่อยู่นอกฐานข้อมูลจริง ๆ

นี่เป็นหนึ่งในการถกเถียงที่ร้อนแรงที่สุดของวงการซอฟต์แวร์มานานหลายทศวรรษ ฝ่ายหนึ่งมองว่าสโตร์โพรซีเจอร์เป็นที่อยู่ตามธรรมชาติของตรรกะการแปลงข้อมูลทั้งหมด อีกฝ่ายห้ามใช้โดยสิ้นเชิง เว็บบอร์ดของนักพัฒนาเต็มไปด้วยเสียงบ่นของคนที่โค้ดรีวิวถูกตีกลับหรือผลงานถูกวิจารณ์ เพียงเพราะเอาตรรกะไปไว้ในสโตร์โพรซีเจอร์

การพัฒนาโดยมี AI ช่วยได้เปลี่ยนน้ำเสียงของการถกเถียงนี้ ผู้ช่วย AI ไม่เข้าข้างฝ่ายใด แต่ชั่งน้ำหนักแต่ละกรณีตามเหตุผล น่าทึ่งที่ทุกวันนี้ AI เองมักเป็นฝ่ายแนะนำสโตร์โพรซีเจอร์พร้อมอธิบายเหตุผล ได้แก่ งานแบบเซต การเปลี่ยนแปลงแบบอะตอมมิก และขอบเขตความปลอดภัยที่ชัดเจน ส่วนที่เหลือของบทความนี้คือการให้เหตุผลทีละกรณีนั้น

สโตร์โพรซีเจอร์คุ้มค่าตรงไหน

ผมเขียนและรีวิวทั้ง SQL และโค้ดแอปพลิเคชันเป็นจำนวนมาก และไม่ยึดติดกับความเชื่อของฝ่ายใดฝ่ายหนึ่ง สโตร์โพรซีเจอร์เป็นเครื่องมือที่ถูกต้องเมื่อตรรกะนั้นเป็นข้อความเกี่ยวกับตัวข้อมูลจริง ๆ ไม่ใช่เกี่ยวกับการนำเสนอหรือการแสดงภาพของข้อมูล

  • งานแบบเซต การย้ายข้อมูลหนึ่งล้านแถวด้วย MERGE เพียงคำสั่งเดียว ดีกว่าการดึงผ่านเครือข่าย วนลูปด้วย C# หรือ Python แล้วส่งกลับ
  • ไม่มีการไปกลับผ่านเครือข่าย ตรรกะทางธุรกิจในโค้ดแอปพลิเคชันต้องดึงทุกแถวที่ต้องการออกจากฐานข้อมูล แล้วส่งผลลัพธ์ทุกตัวกลับมาบันทึก ซึ่งทำให้ปริมาณข้อมูลเพิ่มเป็นสองเท่า เพิ่มความหน่วงในทุกขั้นตอน และทวีคูณไปกับทุกการเรียก ส่วนโพรซีเจอร์อ่าน คำนวณ และเขียนในที่เดียว มีเพียงคำตอบสุดท้ายเท่านั้นที่ข้ามเครือข่าย ต้นทุนที่ซ่อนอยู่เกิดขึ้นที่ฝั่งเซิร์ฟเวอร์ การเรียกเล็ก ๆ นับพันครั้งหมายถึงการเชื่อมต่อพร้อมกันนับพัน และทุกคำขอที่กำลังทำงานจะยึดเธรดทำงานไว้หนึ่งตัว ขีดจำกัดของเธรดผูกกับจำนวนคอร์ เธรดจึงหมดในขณะที่ CPU ยังดูใช้งานน้อย ทางออกเดียวคือซื้อ vCore เพิ่มเพียงเพื่อรองรับการเชื่อมต่อ และสุดท้ายค่าใช้จ่ายของฐานข้อมูลก็สูงกว่าการให้ตรรกะอยู่ในฐานข้อมูล
  • การเปลี่ยนแปลงแบบอะตอมมิกข้ามหลายตาราง ธุรกรรมที่ต้องสำเร็จหรือล้มเหลวพร้อมกันทั้งก้อนจะปลอดภัยที่สุดเมื่ออยู่ในที่ที่ข้อมูลอยู่
  • การดีบัก คุณสามารถรันโพรซีเจอร์กับข้อมูลจริง เดินผ่านทีละขั้น และตรวจผลลัพธ์ระหว่างทางทุกจุดด้วย SELECT ธรรมดา การจำลองบั๊กก็แค่รันซ้ำด้วยพารามิเตอร์เดิม ส่วนการไล่ตามกฎข้อเดียวกันผ่านคอนโทรลเลอร์ เซอร์วิส ORM และล็อกของแอปนั้นยากกว่ามาก
  • การควบคุมเวอร์ชันและการดีพลอย โปรเจกต์ฐานข้อมูลของ Microsoft SQL Server แก้ปัญหานี้ไปหลายปีแล้ว โพรซีเจอร์อยู่ใน Git เหมือนโค้ดอื่น ๆ และไปป์ไลน์ GitHub Actions จะเทียบโปรเจกต์กับฐานข้อมูลปลายทางแล้วนำไปใช้เฉพาะส่วนที่เปลี่ยน การดีพลอยโพรซีเจอร์มักเล็กกว่าและเครียดน้อยกว่าการปล่อยแอปทั้งเวอร์ชัน
  • ความสมบูรณ์ของข้อมูล ข้อจำกัด ทริกเกอร์ และโพรซีเจอร์ที่บังคับใช้เงื่อนไขคงที่ ช่วยปกป้องข้อมูลจากไคลเอนต์ทุกตัว รวมถึงตัวที่ไม่มีใครจำได้ว่าใครเขียนไว้
  • สิทธิ์การเข้าถึง การให้สิทธิ์ EXECUTE บนโพรซีเจอร์ในขณะที่ปฏิเสธการเข้าถึงตารางโดยตรง เป็นขอบเขตความปลอดภัยที่ชัดเจนและตรวจสอบได้
  • งานแบตช์และ ETL การโหลด กำจัดข้อมูลซ้ำ และกระทบยอดไฟล์ใกล้กับข้อมูลทำได้รวดเร็วและเรียบง่าย

จุดที่เจ็บปวด

สโตร์โพรซีเจอร์ไม่ได้ปราศจากข้อแลกเปลี่ยน ต่อไปนี้คือข้อแลกเปลี่ยนที่เกิดขึ้นจริง

  • การขยายขนาดไม่สมดุล การเพิ่มเซิร์ฟเวอร์แอปพลิเคชันราคาถูก แต่ CPU ของฐานข้อมูลเป็นสิ่งที่แพงที่สุดในการเพิ่ม การคำนวณที่กิน CPU หนักและไม่จำเป็นต้องอยู่ติดกับข้อมูล เหมาะจะอยู่ในโค้ดมากกว่า
  • ความสามารถในการย้ายหายไป โค้ดเชิงกระบวนการที่ผูกกับภาษาถิ่นของผู้ให้บริการรายหนึ่งจะผูกธุรกิจไว้กับผู้ขายรายเดียว และการย้ายระบบกลายเป็นการเขียนใหม่
  • ความรู้ถูกแยกเป็นไซโล นักพัฒนาที่อ่าน SQL เชิงกระบวนการได้คล่องมีน้อย กฎต่าง ๆ จึงมีคนเข้าใจเพียงหนึ่งหรือสองคน คำแนะนำ «อย่าเอาตรรกะไว้ในฐานข้อมูล» ที่พูดกันมาหลายปีทำให้ผู้เชี่ยวชาญ SQL ตัวจริงหายากอย่างแท้จริง บริษัทที่มีคนเหล่านี้ควรปฏิบัติต่อพวกเขาเหมือนบุคลากรหลักและพยายามรักษาไว้

การพัฒนาโดยมี AI ช่วยเปลี่ยนอะไร

เครื่องมือเขียนโค้ดด้วย AI ได้ขจัดข้อคัดค้านเก่า ๆ ต่อโค้ดฐานข้อมูลไปเกือบทั้งหมด

ผู้ช่วย AI รีแฟกเตอร์โพรซีเจอร์ ไล่ตามการพึ่งพากันตลอดทั้งสคีมา และรีวิว SQL ได้คล่องพอ ๆ กับโค้ดแอปพลิเคชัน การซื้อเครื่องมือวิเคราะห์โค้ด SQL เฉพาะทางแทบไม่มีเหตุผล เมื่อผู้ช่วยเขียนโค้ดด้วย AI ของคุณทำงานนี้อยู่แล้ว

AI ยังเก่งมากในการเขียนและปรับแต่ง SQL แบบเซต งานหนักด้านข้อมูลที่ควรอยู่ในฐานข้อมูลจึงทำให้ถูกต้องได้ถูกกว่าแต่ก่อน

ยังมีข้อควรระวังอยู่หนึ่งข้อ ให้ผู้ช่วยเห็นสคีมาจริง ทริกเกอร์ สิทธิ์ และปริมาณข้อมูลจริง เพราะโพรซีเจอร์ที่อ่านโดยแยกจากบริบทอาจดูถูกต้องแต่ยังล้มเหลวในระบบจริงได้

ตัวอย่างจริง: ตรรกะอยู่ในฐานข้อมูล แต่ต้นทุนต่ำ

การเก็บตรรกะไว้ในฐานข้อมูลไม่ได้หมายความว่าต้องเรียกฐานข้อมูลทุกครั้งที่มีคนเปิดหน้าเว็บ หน้า Crypto Jobs บน stas.club แสดงให้เห็นว่าทำให้ได้ทั้งสองอย่างได้อย่างไร

ประกาศงานอยู่ในฐานข้อมูล Azure SQL และโพรซีเจอร์ในนั้นตัดสินว่าประกาศใดเกี่ยวกับคริปโตและจัดรูปแบบรายการ นี่คือตรรกะของข้อมูล จึงอยู่ในฐานข้อมูล แต่หน้าสาธารณะที่ใครจะโหลดเมื่อไรก็ได้ จะทำให้ฐานข้อมูลตื่นอยู่ตลอด และฐานข้อมูล Azure SQL แบบ serverless ที่ต้องถูกปลุกให้ตื่นนั้นเสียเงินและอาจทำให้หน้าเว็บค้างหลายนาที

ดังนั้นหน้าเว็บจึงไม่แตะฐานข้อมูลเลย:

  1. งานตามกำหนดเวลารายวันบน Google Cloud เรียก Web API ของเว็บไซต์ ตัวงานเองไม่มีตรรกะทางธุรกิจ งานจริงทำโดย API และโพรซีเจอร์เบื้องหลัง ดังนั้นการรีเฟรชแบบเดียวกันจึงรันด้วยมือได้ด้วย
  2. API รันโพรซีเจอร์และส่งรายการที่เสร็จแล้วกลับมา
  3. งานเขียนรายการนั้นเป็นไฟล์ JSON ลงใน bucket ของ Cloudflare R2 บนระดับฟรี
  4. เมื่อมีคนเปิดหน้าเว็บ เว็บไซต์จะอ่านไฟล์ที่เตรียมไว้จาก R2 ฐานข้อมูลไม่เกี่ยวข้องเลย

ผลลัพธ์คือเรียกฐานข้อมูลวันละหนึ่งครั้งแทนที่จะเรียกหนึ่งครั้งต่อผู้เข้าชมหนึ่งคน กฎยังอยู่ที่เดียว หน้าเว็บโหลดทันที และฐานข้อมูลหลับได้ตลอดทั้งวันที่เหลือ

หลักคร่าว ๆ สำหรับตัดสินใจ

ถามว่าตรรกะนั้นเกี่ยวกับอะไร ถ้ามันอธิบายว่าข้อมูลต้องถูกจัดรูปแบบ ย้าย หรือปกป้องอย่างไร มันอยู่ในฐานข้อมูล ถ้ามันต้องการสิ่งที่อยู่นอกฐานข้อมูล เช่น ข้อมูลภายนอกแบบสด การเรียกเครือข่าย หรือส่วนติดต่อผู้ใช้ มันอยู่ในโค้ด

ตรรกะที่ที่เหมาะกว่าเหตุผล
โหลดจำนวนมาก รวมข้อมูล กำจัดข้อมูลซ้ำสโตร์โพรซีเจอร์เป็นแบบเซตและอยู่ติดกับข้อมูล
กฎความสมบูรณ์เชิงอ้างอิงและความไม่ซ้ำข้อจำกัดบังคับใช้กับไคลเอนต์ทุกตัว
การควบคุมการเข้าถึงระดับแถวสิทธิ์ของฐานข้อมูลจุดบังคับใช้จุดเดียว
การตั้งราคา ส่วนลด การให้คะแนนสโตร์โพรซีเจอร์เป็นแบบเซต ให้คำตอบเดียวกับผู้ใช้ทุกราย ตรวจสอบง่าย
เวิร์กโฟลว์และสถานะการอนุมัติสโตร์โพรซีเจอร์การเปลี่ยนสถานะที่อนุญาตถูกบังคับและตรวจสอบได้ในที่เดียว
กฎที่ต้องใช้ข้อมูลสด (ราคาตลาด ฟีด API)โค้ดแอปพลิเคชันข้อมูลอยู่นอกฐานข้อมูล
การเรียกบริการภายนอกโค้ดแอปพลิเคชันฐานข้อมูลไม่ควรเรียกผ่านเครือข่าย

คำตัดสิน

สโตร์โพรซีเจอร์เป็นที่อยู่ที่ดีของตรรกะทางธุรกิจ ไม่ใช่ที่อยู่ที่แย่ กฎที่เกี่ยวกับข้อมูล เช่น การให้คะแนน การตั้งราคา สถานะเวิร์กโฟลว์ และความสมบูรณ์ ควรอยู่ติดกับข้อมูล ที่นั่นมันทำงานแบบเซต ให้คำตอบเดียวกับผู้ใช้ทุกราย และตรวจสอบง่าย เก็บโค้ดแอปพลิเคชันไว้สำหรับสิ่งที่อยู่นอกฐานข้อมูลจริง ๆ ได้แก่ ข้อมูลภายนอกแบบสด การเรียกเครือข่าย และส่วนติดต่อผู้ใช้

วิศวกรบางคนจะยังไม่เห็นด้วย และบางคนมีเหตุผลจริง เช่น ทีมที่มีทักษะ SQL น้อย หรือฐานข้อมูลที่ใช้กำลังประมวลผลจนถึงขีดจำกัดแล้ว สำหรับทุกคนที่เหลือ ให้ถามว่ากฎนั้นเกี่ยวกับอะไร แล้ววางไว้ในที่ที่ข้อมูลนั้นอยู่ และเลือกอย่างนี้ด้วยความตั้งใจ ไม่ใช่ด้วยความเคยชิน
