บทความนี้พูดถึงการเลือกฐานข้อมูลสำหรับโปรเจกต์ใหม่ที่เริ่มจากศูนย์ คำตอบสั้น ๆ คือ ในฐานะเอนจินฐานข้อมูล Postgres ใช้ได้ดี แต่ในฐานะแพลตฟอร์มที่ใช้งานจริง ขึ้นอยู่กับขั้นตอน CI/CD ของคุณและเครื่องมือที่ต้องใช้รอบฐานข้อมูล

นี่คือวิธีที่ผมคิดเรื่องนี้ หลังจากสร้างซอฟต์แวร์มาสามทศวรรษทั้งสองฝั่งของรั้วนี้

คำถามเบื้องหลังคำถาม

"ควรเริ่มต้นด้วยฐานข้อมูลไหน" จริง ๆ แล้วคือสามคำถาม:

  • งานคืออะไร ไม่มีใครจ่ายเงินให้ SQL Server เพียงเพื่อเก็บข้อมูล เราใช้มันเพื่อทำงานกับข้อมูล: สโตร์โพรซีเดอร์ การแปลงข้อมูลแบบเซต งานที่ตั้งเวลา ETL และการรายงาน โดยให้ตรรกะทางธุรกิจทำงานอยู่ข้างข้อมูลโดยตรง ให้กำหนดภาระงานนี้ก่อน แล้วค่อยถามว่า Postgres ทำได้หรือไม่
  • มีความสามารถที่ผมต้องการหรือเปล่า ฟีเจอร์ที่ภาระงานของผมพึ่งพาอยู่ตอนนี้: โพรซีเดอร์ การตั้งเวลา ETL การรายงาน ความปลอดภัย เครื่องมือ ไม่มีใครเลือกฐานข้อมูลเพื่อให้ย้ายออกได้ภายหลัง ดังนั้นเกณฑ์คือมันทำสิ่งที่ผมต้องการตอนนี้ได้หรือไม่
  • ค่าใช้จ่ายเท่าไร ข้อนี้ตามมาจากสองคำตอบแรก เพราะงานเป็นตัวกำหนดสูตร ภาระงานหนักที่คงที่คิดราคาตามจำนวนแกน CPU ที่คุณเปิดไว้ ส่วนภาระงานที่ขึ้นลงคิดตามความถี่ที่ถูกเรียกและความหนักของแต่ละงาน ซึ่งตรงนั้นระดับแบบจ่ายตามการใช้งานหรือ serverless อาจชนะ ส่วนค่าไลเซนส์ ค่าโฮสติ้ง และค่าแรงคนจะเพิ่มเข้ามาอีก

ขึ้นอยู่กับงาน การเก็บและสืบค้นข้อมูล: ง่าย การทำงานกับข้อมูลภายในฐานข้อมูล: Postgres จัดการ SQL และโค้ดเชิงกระบวนการได้ดี แต่ไม่ครอบคลุมแพลตฟอร์มรอบ ๆ (การตั้งเวลา ETL การรายงาน) คำถามที่สองบอกว่าภาระงานของคุณอยู่ฝั่งไหน ส่วนคำถามที่สาม คือต้นทุน ตามมาจากสองข้อแรก: คุณจ่ายให้ CPU ที่เปิดตลอดเวลา หรือจ่ายตามความถี่และความหนักของการเรียกฐานข้อมูล

Postgres ตอนนี้อยู่ตรงไหน

PostgreSQL 18 ออกเมื่อวันที่ 25 กันยายน 2025 ไฮไลต์คือระบบย่อย I/O แบบอะซิงโครนัสใหม่ ซึ่งโครงการระบุว่าอ่านจากหน่วยเก็บข้อมูลได้เร็วขึ้นสูงสุด 3 เท่า นอกจากนี้ยังเก็บสถิติของตัววางแผนไว้ข้ามการอัปเกรดเวอร์ชันหลัก ซึ่งช่วยขจัดอาการช้าหลังอัปเกรดที่น่าปวดหัวอย่างหนึ่ง สิ่งที่เพิ่มมาสำหรับนักพัฒนา ได้แก่ คอลัมน์ที่สร้างขึ้นแบบเสมือน uuidv7() การพิสูจน์ตัวตนด้วย OAuth 2.0 OLD และ NEW ในอนุประโยค RETURNING และข้อจำกัดเชิงเวลา

นี่ไม่ใช่ Postgres ของปี 2010 อีกแล้ว ข้อโต้แย้งแบบ "SQL Server ทำได้ แต่ Postgres ทำไม่ได้" ส่วนใหญ่ที่ผมจำได้ได้หมดอายุไปอย่างเงียบ ๆ

SQL Server ตอนนี้อยู่ตรงไหน

SQL Server 2025 เปิดให้ใช้งานทั่วไปที่งาน Ignite เมื่อเดือนพฤศจิกายน 2025 Microsoft วางตำแหน่งให้เป็นฐานข้อมูลที่พร้อมสำหรับ AI: ชนิดเวกเตอร์แบบเนทีฟ ดัชนีเวกเตอร์บน DiskANN การจัดการโมเดลจาก T-SQL ชนิด JSON แบบเนทีฟพร้อมการทำดัชนี เรกูลาร์เอ็กซ์เพรสชันใน T-SQL การเรียก REST ในตัว และการสตรีมเหตุการณ์การเปลี่ยนแปลง การทำมิเรอร์ของ Fabric ส่งข้อมูลไปยัง OneLake เพื่อการวิเคราะห์

เป็นรุ่นที่แข็งแกร่ง และมุ่งเป้าตรงไปยังนักพัฒนาที่อยู่ในโลกของ Microsoft อยู่แล้ว

จุดที่ Postgres ชนะ

  • การออกใบอนุญาต ไม่มีค่าธรรมเนียมต่อแกน ต่อเอดิชัน หรือ Software Assurance เมื่อคุณรันเอง ส่วนบริการคลาวด์แบบจัดการ ไลเซนส์รวมอยู่ในราคาแล้ว จึงสำคัญน้อยลงมากตรงนั้น
  • ความสามารถในการพกพา รันได้บน Linux, macOS, Windows, คอนเทนเนอร์ และมีบริการแบบจัดการในคลาวด์รายใหญ่ทุกแห่ง ผูกติดกับผู้ให้บริการน้อยกว่า
  • ความสามารถในการขยาย ส่วนขยายอย่าง PostGIS และ pgvector ชนิดข้อมูลที่กำหนดเอง และภาษาเชิงกระบวนการหลายภาษา
  • มาตรฐานและฟีเจอร์ JSONB อาร์เรย์ ชนิดช่วง ดัชนีบางส่วนและดัชนีนิพจน์ และ DDL แบบทรานแซกชัน (ย้อนกลับการเปลี่ยนสคีมาได้)

จุดที่ SQL Server ยังชนะ

  • CI/CD และการควบคุมซอร์สโค้ด จุดแข็งที่สุดของ SQL Server ฐานข้อมูลอยู่ในระบบควบคุมซอร์สเป็นโปรเจกต์ และเครื่องมือสร้างการดีพลอยให้คุณ Postgres ไม่มีสิ่งเทียบเท่าที่เป็นมาตรฐาน คุณจึงต้องเขียนและดูแลสคริปต์ย้ายข้อมูลด้วยมือ รายละเอียดอยู่ในหัวข้อถัดไป
  • เครื่องมือ SSMS, SQL Agent, SSIS, SSRS และ Profiler เป็นชุดเครื่องมือที่ผสานกันแน่นและขัดเกลามาอย่างดี ใน Postgres คุณต้องประกอบชุดของตัวเองจาก pgAdmin, cron หรือ pg_cron และเครื่องมือของบุคคลที่สาม
  • การผสานกับ Microsoft Active Directory และ Entra, .NET, Power BI, Fabric ถ้าทั้งบริษัทของคุณใช้ Microsoft อยู่แล้ว แรงเสียดทานจะน้อยกว่า
  • ฟีเจอร์ระดับองค์กรในตัว Columnstore, OLTP ในหน่วยความจำ และ Always On availability groups ที่เติบโตเต็มที่ ถูกแพ็กเกจและให้การสนับสนุนเป็นผลิตภัณฑ์เดียว
  • จุดติดต่อเดียว ผู้ให้บริการรายเดียวรับผิดชอบทุกอย่าง กับ Postgres คุณต้องเลือกผู้ให้บริการแบบจัดการหรือบริษัทซัพพอร์ตมาทำหน้าที่นั้น
  • ระดับราคา เอดิชันและระดับบริการของ SQL Server ทำให้ภาระงานเล็กมีค่าใช้จ่ายต่ำกว่าระดับกลางทั่วไปมาก Postgres ไม่มีลำดับขั้นแบบนั้น: เป็นเอนจินเดียวกันทุกที่ ต้นทุนที่ปลายเล็กจึงถูกกำหนดโดยโฮสติ้งที่คุณเลือก ไม่ใช่เอดิชันเริ่มต้นราคาถูก

Postgres ยังกำลังไล่ตามอยู่

เอนจินจัดเก็บและแกน SQL ของ Postgres เติบโตเต็มที่มาก ส่วนชั้นที่ห่อหุ้มมัน คือฟีเจอร์ที่องค์กรใหญ่คาดหวังให้มีมาให้พร้อมใช้ ยังใหม่กว่า และ Postgres ใช้เวลาหลายรุ่นที่ผ่านมาปิดช่องว่างที่ SQL Server ปิดไปนานแล้ว:

  • สโตร์โพรซีเดอร์ที่ควบคุมทรานแซกชันได้ มาถึงใน PostgreSQL 11 (2018) T-SQL มีโพรซีเดอร์มาตั้งแต่ยุคแรก
  • MERGE เพิ่งมาถึงใน PostgreSQL 15 (2022) ส่วน SQL Server มีมาตั้งแต่ 2008
  • คอลัมน์ที่สร้างขึ้นแบบเสมือน เป็นของใหม่ใน PostgreSQL 18 SQL Server มีคอลัมน์คำนวณมาหลายสิบปีแล้ว
  • OLD และ NEW ใน RETURNING (PostgreSQL 18) คือคำตอบของ Postgres ต่ออนุประโยค OUTPUT inserted/deleted ใน T-SQL
  • ข้อจำกัดเชิงเวลา (PostgreSQL 18) ขยับเข้าใกล้ตารางเชิงเวลาที่ SQL Server เปิดตัวในปี 2016
  • การพิสูจน์ตัวตนด้วย OAuth 2.0 (PostgreSQL 18) คือเรื่องราวของ single sign-on ที่ SQL Server ได้ผ่าน Active Directory และ Entra

ทุกรุ่นทำให้ Postgres เข้าใกล้ SQL Server มากขึ้น แต่ช่องว่างที่เหลือเป็นตัวตัดสินโปรเจกต์จริง และช่องที่ใหญ่ที่สุดคือ CI/CD เมื่อไม่มีวิธีมาตรฐานในการกำหนดฐานข้อมูลในระบบควบคุมซอร์สแล้วดีพลอยจากไปป์ไลน์ ทุกการเปลี่ยนแปลงก็ต้องแลกด้วยสคริปต์ย้ายข้อมูลที่เขียนด้วยมือ สำหรับทีมที่อยากให้ฐานข้อมูลถูกกำหนดด้วยไฟล์ซอร์ส นี่เป็นข้อเสียร้ายแรงและอาจเป็นตัวตัดสินได้เลย

CI/CD และการควบคุมซอร์สโค้ด: ชัยชนะที่ใหญ่ที่สุดของ SQL Server

นี่คือจุดแข็งที่สุดของ SQL Server เหนือ Postgres และเป็นสิ่งแรกที่ผมจะชั่งน้ำหนัก

ใน SQL Server ฐานข้อมูลเป็นโปรเจกต์ในระบบควบคุมซอร์ส ตาราง โพรซีเดอร์ วิว และทริกเกอร์เป็นไฟล์ CREATE ธรรมดา และเครื่องมือ (โปรเจกต์ฐานข้อมูล SSDT, sqlpackage) จะเปรียบเทียบโปรเจกต์นั้นกับฐานข้อมูลที่ใช้งานอยู่และสร้างการดีพลอยให้คุณ คุณแก้ไขสถานะที่ต้องการ แล้วเครื่องมือคำนวณการเปลี่ยนแปลงเอง ต่อเข้ากับ Visual Studio, Azure DevOps และ GitHub Actions ได้โดยตรง

Postgres ไม่มีสิ่งเทียบเท่าที่เป็นมาตรฐาน วิธีหลักคือสคริปต์ย้ายข้อมูล: ทุกการเปลี่ยนแปลงคุณเขียนสคริปต์ที่มีหมายเลขกำกับด้วยมือ เพื่อพาฐานข้อมูลจากเวอร์ชันหนึ่งไปอีกเวอร์ชัน และเก็บไว้ทั้งหมดตลอดไป เครื่องมืออย่าง Flyway และ Liquibase สามารถรันสคริปต์เหล่านั้นอัตโนมัติจากไปป์ไลน์ได้ แต่คนยังต้องเขียนทุกสคริปต์ด้วยมือก่อนคอมมิต ใน SQL Server คุณคอมมิตสถานะที่ต้องการ แล้วไปป์ไลน์คำนวณและดีพลอยการเปลี่ยนแปลงเอง มีเครื่องมือแบบอิงสถานะที่เทียบไฟล์กับฐานข้อมูลที่ใช้งานอยู่ (เช่น Atlas และ pg-schema-diff) แต่ใหม่กว่า ใช้กันน้อยกว่า และไม่ใช่ของทางการ สโตร์โพรซีเดอร์ยังต้องมีขั้นตอนสร้างใหม่ของคุณเองเพิ่มเข้ามาด้วย

ถ้าคุณอยากให้ฐานข้อมูลถูกกำหนดด้วยไฟล์ซอร์สเท่านั้น และรับไม่ไหวที่จะเขียนและดูแลสคริปต์ย้ายข้อมูลทุกตัวด้วยมือ SQL Server คือทางเลือกที่ปลอดภัยกว่า

Azure Database for PostgreSQL, B1msประมาณ $144 + $45 ที่เก็บข้อมูล (รวมประมาณ $190)ค่าประมวลผลประมาณ $12 ต่อเดือน (US East) 32 GiB คือที่เก็บข้อมูลที่เล็กที่สุดที่จัดสรรได้ การสำรองข้อมูลฟรีไม่เกินขนาดที่เก็บข้อมูลที่จัดสรร

ราคาเหล่านี้เป็นค่าโดยประมาณ ผมนำมาจากบทสรุปของบุคคลที่สาม และราคาที่เก็บข้อมูลของ Postgres เป็นการประมาณของผมเอง (ประมาณ $0.115 ต่อ GiB ต่อเดือน) ตรวจสอบเครื่องคิดราคาของ Azure ก่อนตัดสินใจ

สิ่งที่คุณจ่าย และสิ่งที่คุณรู้สึก เมื่อจำนวนการเรียกเพิ่มขึ้น ราคา $5 และ $15 ของ Azure SQL คงที่สำหรับระดับนั้น คุณจ่ายไม่ว่าฐานข้อมูลจะถูกเรียกวันละครั้งหรือหนึ่งล้านครั้ง สิ่งที่จำกัดคุณคือความจุ เมื่อการเรียกต้องการมากกว่า 5 หรือ 10 DTU ของระดับนั้น คิวรีจะช้าลง และคุณแก้ด้วยการขยับไประดับที่สูงขึ้น ไม่ใช่การจ่ายต่อการเรียก

Postgres ทำงานแบบเดียวกันเรื่องราคา แต่ให้ความรู้สึกต่างออกไปเมื่อถึงขีดจำกัด ราคา B1ms ก็คงที่ต่อชั่วโมงเช่นกัน ไม่ว่าจะมีการเรียกเข้ามากี่ครั้ง แต่ B1ms เป็นเซิร์ฟเวอร์แบบ burstable สร้างมาสำหรับฐานข้อมูลที่ส่วนใหญ่ว่าง ขณะว่างมันสะสมเครดิตเหมือนบัญชีธนาคาร และช่วงที่ยุ่งจะใช้เครดิตนั้น ถ้ายุ่งนานเกินไป เครดิตจะหมดและเซิร์ฟเวอร์อาจหยุดตอบสนอง คุณแก้แบบเดียวกัน คือขยับไปใช้ vCore มากขึ้น ซึ่ง Microsoft บอกว่าใช้เวลาไม่กี่วินาที ดังนั้นกับทั้งสองฐานข้อมูล การเรียกที่มากขึ้นไม่ได้ทำให้บิลสูงขึ้น แต่ผลักคุณไปสู่ระดับที่ใหญ่ขึ้น และระดับที่ใหญ่ขึ้นนั่นเองที่ทำให้บิลสูงขึ้น

ข้อเสนอฟรีและ serverless เป็นข้อยกเว้น พวกมันคิดเงินตามการประมวลผลที่ใช้จริงเป็นรายวินาที ความถี่ของการเรียกจึงมีผลโดยตรง: การเรียกถี่ ๆ ทำให้ฐานข้อมูลตื่นอยู่และใช้โควตาฟรีหมดไป

สำหรับภาระงานนี้ คำตอบขึ้นอยู่กับว่าฐานข้อมูลตื่นอยู่กี่ชั่วโมงต่อวัน ถ้าแอปปลุกฐานข้อมูลครั้งละไม่กี่นาทีแล้วเงียบไป ข้อเสนอฟรีก็ครอบคลุม ถ้าโควตารายเดือนหมด คุณเลือกระหว่างหยุดฐานข้อมูลชั่วคราวไปถึงเดือนหน้ากับจ่ายตามอัตรามาตรฐาน

Postgres บน Azure มีราคาขั้นต่ำ B1ms ประมาณ $12 ต่อเดือนเฉพาะค่าประมวลผล หรือราว $144 ต่อปีก่อนรวมที่เก็บข้อมูลและการสำรองข้อมูล ไม่ว่าจะมีใครใช้หรือไม่ ผมไม่พบสิ่งที่เทียบเท่ากับการหยุดอัตโนมัติของ serverless คุณหยุดเซิร์ฟเวอร์แบบยืดหยุ่นได้ แต่ Azure จะเริ่มใหม่ให้อัตโนมัติหลังผ่านไป 7 วัน หากคุณไม่เริ่มเองก่อน ระดับ burstable ยังออกแบบมาสำหรับภาระงานที่ว่างอยู่หรืออยู่ต่ำกว่าเส้นฐาน: ถ้า CPU สูงต่อเนื่อง เครดิตจะหมดและเซิร์ฟเวอร์อาจเข้าถึงไม่ได้ และ Microsoft อธิบายว่าระดับนี้ใช้สำหรับสภาพแวดล้อมที่ไม่ใช่โปรดักชันเป็นหลัก

มีสองสิ่งที่อาจเปลี่ยนภาพได้:

  • การแชร์ เซิร์ฟเวอร์ Postgres หนึ่งตัวโฮสต์ได้หลายฐานข้อมูล ดังนั้นถ้าทุกโปรเจกต์ของคุณอยู่บนเซิร์ฟเวอร์เดียว ค่า $12 จะถูกหารกัน ข้อเสนอฟรีของ SQL Server นับต่อฐานข้อมูล
  • โหลดคงที่ ถ้าแอปเข้าถึงฐานข้อมูลตลอด 24 ชั่วโมง โควตาฟรีของ SQL (ราว 28 ชั่วโมงของ vCore หนึ่งตัว) จะหมดเร็ว และคุณจะจ่ายอัตรา serverless มาตรฐาน ผมไม่พบอัตราต่อวินาทีปัจจุบัน ดังนั้นก่อนตัดสินใจ ให้คิดราคาทั้งสองตัวเลือกในเครื่องคิดเลขของ Azure ด้วยโหลดจริงของคุณ

สรุป: Postgres ไม่ได้ถูกกว่า การบอกว่าถูกกว่าเป็นความเชื่อผิด ๆ ที่พบบ่อย ซอฟต์แวร์ฟรี แต่บนบริการคลาวด์แบบจัดการ คุณจ่ายค่าประมวลผลและที่เก็บข้อมูล ไม่ใช่ค่าไลเซนส์ และไลเซนส์ของ SQL Server รวมอยู่ในราคาอยู่แล้วไม่ว่ากรณีใด ที่ 20 GB ตัวเลือก SQL Server ที่ถูกที่สุดเท่ากับหรือดีกว่า Postgres ในทุกระดับการใช้งาน: ฟรีจนถึงประมาณ 2 ชั่วโมงที่ตื่นต่อวัน จากนั้น Standard S0 ประมาณ $180 ต่อปี เทียบกับ Postgres ประมาณ $190 ส่วนต่างที่ S0 เล็กน้อย ให้อ่านว่า Postgres ดีที่สุดก็แค่พอ ๆ กัน และไม่เคยถูกกว่าอย่างชัดเจน สำหรับข้อเสนอฟรีที่ทำให้เรื่องนี้เป็นไปได้ ดู Hunting Freebies in the Clouds ซึ่งเปรียบเทียบข้อเสนอฐานข้อมูลและการประมวลผลฟรีจาก Azure, Google, AWS, Oracle และ Cloudflare

วิธีตัดสินใจเชิงปฏิบัติ

ผมจะเลือก Postgres เมื่อ:

  • ฐานข้อมูลเล็กและส่วนใหญ่เป็นตารางกับวิวที่ไม่เคยเปลี่ยนแปลงหรือพัฒนา
  • ไลเซนส์เป็นรายการค่าใช้จ่ายที่มีนัยสำคัญ หรือคุณถูกบีบเรื่องจำนวนแกน
  • คุณอยากรันฐานข้อมูลเดียวกันบนคลาวด์ใดก็ได้หรือบนแล็ปท็อป
  • ทีมของคุณรู้จัก Postgres อยู่แล้ว หรืออยากเรียนรู้

ผมจะเลือก SQL Server เมื่อ:

  • สคีมา SQL ของคุณเปลี่ยนบ่อยและ CI/CD สำคัญ: คุณอยากให้ฐานข้อมูลถูกกำหนดในระบบควบคุมซอร์สและดีพลอยจากไปป์ไลน์โดยไม่ต้องใช้สคริปต์ย้ายข้อมูลที่เขียนด้วยมือ
  • ตรรกะทางธุรกิจส่วนใหญ่ของคุณจะอยู่ในสโตร์โพรซีเดอร์
  • คุณต้องการ SSIS, SSRS และ SQL Agent เป็นส่วนหนึ่งของแพลตฟอร์ม
  • บริษัทผูกพันกับสแต็กของ Microsoft รวมถึง Fabric และ Power BI

ถ้าคุณยังลังเล ให้ชั่งน้ำหนัก CI/CD ก่อน

บทสรุป

Postgres ใช้ได้กับโปรเจกต์เล็กจิ๋วที่ต้องการแค่การเก็บข้อมูลถาวรขั้นพื้นฐาน สำหรับอะไรที่ใหญ่กว่านั้น การเลือกขึ้นอยู่กับงาน ความสามารถที่คุณต้องการรอบฐานข้อมูล และที่สำคัญที่สุดคือขั้นตอน CI/CD ของคุณ ซึ่งเป็นจุดที่ SQL Server ชนะชัดเจนที่สุด ถ้าคุณอยากพุชคอมมิตแล้วให้ฐานข้อมูลดีพลอยตัวเอง ให้เริ่มด้วย SQL Server
