Мой короткий ответ: логику, которая формирует данные, держите в базе данных, а код приложения оставьте для того, что на самом деле живёт за её пределами.

Это один из самых жарких споров в программировании на протяжении десятилетий. Один лагерь считает хранимые процедуры естественным домом для всей логики преобразования данных, другой — запрещает их полностью. Форумы разработчиков полны жалоб людей, чьи код-ревью отклоняли или чью работу критиковали только за то, что они помещали логику в хранимые процедуры.

Разработка с помощью ИИ изменила тон этого спора. Вместо того чтобы примкнуть к одному из лагерей, ИИ-ассистент взвешивает каждый случай по существу. Поразительно, как часто теперь сам ИИ предлагает хранимую процедуру и объясняет почему: работа над множествами, атомарные изменения, чёткая граница безопасности. Остальная часть этой статьи — именно такие рассуждения для каждого случая.

Где хранимые процедуры заслуживают своего места

Я много пишу и проверяю и SQL, и код приложений, и не разделяю догм ни одной из сторон. Хранимые процедуры — правильный инструмент, когда логика на самом деле является утверждением о данных, а не об их представлении или визуализации.

  • Работа над множествами. Перенести миллион строк одним MERGE лучше, чем тянуть их по сети, обходить в цикле на C# или Python и отправлять обратно.
  • Никаких сетевых обращений туда и обратно. Бизнес-логика в коде приложения вынуждена вытягивать из базы каждую нужную строку, а затем отправлять каждый результат обратно для сохранения. Это удваивает трафик, добавляет задержку на каждом шаге и умножается с каждым вызовом. Процедура читает, вычисляет и записывает в одном месте, и по сети проходит только итоговый ответ. Скрытая цена — на стороне сервера. Тысячи мелких вызовов — это тысячи одновременных соединений, и каждый активный запрос занимает рабочий поток. Лимиты потоков привязаны к числу ядер, поэтому потоки заканчиваются, пока процессор кажется недогруженным. Единственный выход — покупать больше vCore лишь для того, чтобы удерживать соединения, и счёт за базу данных в итоге оказывается выше, чем если бы логика жила внутри неё.
  • Атомарные изменения в нескольких таблицах. Транзакция, которая должна либо полностью завершиться, либо полностью откатиться, надёжнее всего там, где лежат данные.
  • Отладка. Можно запустить процедуру на реальных данных, пройти её по шагам и посмотреть каждый промежуточный результат обычным SELECT. Воспроизвести ошибку — значит запустить процедуру ещё раз с теми же параметрами. Искать то же правило среди контроллеров, сервисов, ORM и логов приложения — гораздо более трудная задача.
  • Контроль версий и развёртывание. Проекты баз данных SQL Server от Microsoft решили это много лет назад. Процедуры лежат в Git, как любой другой код, а конвейер GitHub Actions сравнивает проект с целевой базой и применяет только изменения. Развёртывание процедуры часто меньше и спокойнее, чем выпуск версии приложения.
  • Целостность данных. Ограничения, триггеры и процедуры, обеспечивающие инварианты, защищают данные от любого клиента, включая те, которые никто уже не помнит.
  • Права доступа. Выдать EXECUTE на процедуру и запретить прямой доступ к таблицам — чистая, поддающаяся аудиту граница безопасности.
  • Пакетные задания и ETL. Загружать, дедуплицировать и сверять файлы рядом с данными быстро и просто.

Где они мешают

У хранимых процедур есть свои компромиссы. Вот настоящие.

  • Масштабирование несимметрично. Серверы приложений добавлять дёшево, а процессор базы данных — самый дорогой из того, что можно добавить. Ресурсоёмкие вычисления, которым не нужно находиться рядом с данными, лучше выполнять в коде.
  • Теряется переносимость. Процедурный код, привязанный к диалекту, привязывает бизнес к одному поставщику, а миграция превращается в переписывание.
  • Знания замыкаются в узком круге. Процедурный SQL свободно читают немногие разработчики, поэтому правила оказываются понятны одному-двум людям. Годы советов «держите логику вне базы данных» сделали настоящих специалистов по SQL по-настоящему редкими. Компаниям, у которых они есть, стоит относиться к ним как к ключевым сотрудникам и прилагать усилия, чтобы их удержать.

Что меняет разработка с помощью ИИ

ИИ-ассистент рефакторит процедуры, прослеживает зависимости по всей схеме и проверяет SQL так же легко, как код приложения. Покупать специализированный анализатор SQL-кода нет особого смысла, когда ваш ИИ-ассистент для программирования уже делает эту работу.

ИИ также очень хорошо пишет и оптимизирует SQL, работающий над множествами, поэтому ёмкую по данным работу, которой место в базе, теперь дешевле сделать правильно, чем раньше.

Остаётся одна оговорка. Дайте ассистенту реальную схему, триггеры, права и объёмы данных: процедура, прочитанная в отрыве от контекста, может выглядеть правильно и всё равно сломаться в продакшене.

Реальный пример: логика в базе данных при низких затратах

Держать логику в базе данных не значит обращаться к базе при каждом просмотре страницы. Страница Crypto Jobs на stas.club показывает, как совместить и то и другое.

Вакансии лежат в базе Azure SQL, а процедуры в ней решают, какие вакансии относятся к криптовалютам, и формируют список. Это логика данных, поэтому она остаётся в базе. Но публичная страница, которую кто угодно может открыть в любой момент, не давала бы базе уснуть, а бессерверной базе Azure SQL, которую приходится «будить», это стоит денег и может подвесить страницу на несколько минут.

Поэтому страница вообще не обращается к базе:

  1. Ежедневное запланированное задание в Google Cloud вызывает веб-API сайта. В самом задании нет бизнес-логики: работу выполняют API и стоящие за ним процедуры, так что то же обновление можно запустить и вручную.
  2. API запускает процедуры и возвращает готовый список.
  3. Задание записывает этот список как файл JSON в бакет Cloudflare R2 на бесплатном тарифе.
  4. Когда кто-то открывает страницу, сайт читает подготовленный файл из R2. База данных вообще не участвует.

В итоге получается один вызов базы в сутки вместо одного на каждого посетителя. Правила по-прежнему живут в одном месте, страница загружается мгновенно, а база может спать до конца дня.

Практическое правило для решения

Спросите, о чём эта логика. Если она описывает, как данные должны формироваться, перемещаться или защищаться, ей место в базе данных. Если ей нужно что-то за пределами базы — живые внешние данные, сетевые вызовы или пользовательский интерфейс, — ей место в коде.

Вердикт

Хранимые процедуры — хороший дом для бизнес-логики, а не плохой. Правила, которые касаются данных, например оценка, ценообразование, статусы рабочих процессов и целостность, должны находиться рядом с ними. Там они работают над множествами, дают всем потребителям одинаковый ответ и легко проверяются. Код приложения оставьте для того, что действительно живёт за пределами базы: живые внешние данные, сетевые вызовы и пользовательский интерфейс.

Некоторые инженеры всё равно не согласятся, и у немногих есть веские причины: команда с небольшим опытом SQL или база, уже упёршаяся в предел вычислительных ресурсов. Всем остальным: спросите, о чём правило, и поместите его туда, где живут эти данные. Делайте этот выбор осознанно, а не по привычке.
