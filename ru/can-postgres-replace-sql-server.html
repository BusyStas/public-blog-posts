Эта статья о выборе базы данных для нового проекта, с нуля. Короткий ответ: как движок базы данных Postgres вполне хорош. Как рабочая платформа он зависит от вашего процесса CI/CD и от инструментов, которые нужны вокруг базы данных.

Вот как я это вижу после трёх десятилетий разработки программного обеспечения по обе стороны этого забора.

Вопрос за вопросом

«С какой базы данных мне начать?» — это на самом деле три вопроса:

  • В чём состоит задача? Никто не платит за SQL Server только ради хранения данных. Мы используем его, чтобы работать с данными: хранимые процедуры, множественные преобразования, задания по расписанию, ETL и отчётность, причём бизнес-логика выполняется рядом с данными. Сначала определите эту нагрузку, а потом спросите, справится ли с ней Postgres.
  • Есть ли в нём нужные мне возможности? Функции, от которых моя нагрузка зависит сегодня: процедуры, планирование, ETL, отчётность, безопасность, инструменты. Никто не выбирает базу данных ради того, чтобы потом уйти с неё, поэтому критерий один: делает ли она то, что мне нужно сейчас.
  • Сколько это стоит? Это следует из первых двух ответов, потому что формулу определяет задача. Постоянная тяжёлая нагрузка оценивается по числу ядер CPU, которые вы держите включёнными. Нерегулярная оценивается по частоте вызовов и тяжести каждой задачи, и там могут выиграть тарифы с оплатой по факту использования или serverless. Лицензии, хостинг и люди добавляются сверху.

Всё зависит от задачи. Хранить данные и делать запросы: легко. Работать с данными внутри базы: Postgres хорошо справляется с SQL и процедурным кодом, но не с платформой вокруг него (планирование, ETL, отчётность). Второй вопрос показывает, на какой стороне ваша нагрузка. Третий, стоимость, вытекает из первых двух: вы платите либо за постоянно включённый CPU, либо за то, как часто и как тяжело вы обращаетесь к базе.

Где сейчас Postgres

PostgreSQL 18 вышел 25 сентября 2025 года. Главное новшество — новая подсистема асинхронного ввода-вывода, которая, по словам проекта, показала до 3 раз более быстрое чтение с диска. Кроме того, он сохраняет статистику планировщика при обновлении между основными версиями, что устраняет одно из самых неприятных замедлений после апгрейда. Среди нововведений для разработчиков: виртуальные генерируемые столбцы, uuidv7(), аутентификация OAuth 2.0, OLD и NEW в предложениях RETURNING и временны́е ограничения.

Это не Postgres 2010 года. Большинство аргументов вида «SQL Server это умеет, а Postgres нет», которые я помню, тихо устарели.

Где сейчас SQL Server

SQL Server 2025 стал общедоступным на конференции Ignite в ноябре 2025 года. Microsoft позиционирует его как базу данных, готовую к ИИ: нативный векторный тип, векторные индексы на основе DiskANN, управление моделями из T-SQL, нативный тип JSON с индексацией, регулярные выражения в T-SQL, встроенные REST-вызовы и потоковая передача событий изменений. Зеркалирование Fabric отправляет данные в OneLake для аналитики.

Это сильный релиз, нацеленный прямо на разработчиков, которые уже живут в мире Microsoft.

Где выигрывает Postgres

  • Лицензирование. Никаких платежей за ядро, за редакцию или за Software Assurance, когда вы запускаете его сами. В управляемом облачном сервисе лицензия включена в цену, поэтому там это значит гораздо меньше.
  • Переносимость. Linux, macOS, Windows, контейнеры и управляемое предложение в каждом крупном облаке. Меньше привязки к поставщику.
  • Расширяемость. Расширения вроде PostGIS и pgvector, пользовательские типы и несколько процедурных языков.
  • Стандарты и возможности. JSONB, массивы, диапазонные типы, частичные индексы и индексы по выражениям, а также транзакционный DDL (изменение схемы можно откатить).

Где SQL Server по-прежнему выигрывает

  • CI/CD и контроль версий. Сильнейшая сторона SQL Server. База данных живёт в системе контроля версий как проект, а инструменты сами генерируют развёртывание. У Postgres нет стандартного аналога, поэтому вы пишете и поддерживаете скрипты миграций вручную. Подробности в разделе ниже.
  • Инструменты. SSMS, SQL Agent, SSIS, SSRS и Profiler образуют тесно интегрированный, отполированный набор. В Postgres вы собираете свой из pgAdmin, cron или pg_cron и сторонних инструментов.
  • Интеграция с Microsoft. Active Directory и Entra, .NET, Power BI, Fabric. Если вся ваша компания работает на Microsoft, трения меньше.
  • Встроенные корпоративные функции. Columnstore, OLTP в памяти и зрелые группы доступности Always On поставляются и поддерживаются как один продукт.
  • Один ответственный. За всё отвечает один поставщик. В случае Postgres на эту роль вы выбираете управляемый сервис или компанию-поддержку.
  • Тарифные уровни. Редакции и уровни обслуживания SQL Server позволяют небольшой нагрузке стоить намного дешевле среднего уровня. В Postgres такой градации нет: везде один и тот же движок, поэтому стоимость на малом конце определяется выбранным хостингом, а не дешёвой начальной редакцией.

Postgres всё ещё догоняет

Движок хранения и ядро SQL у Postgres очень зрелые. Слой вокруг них, то есть функции, которые крупные предприятия ожидают получить из коробки, моложе, и последние несколько релизов Postgres закрывал пробелы, которые SQL Server закрыл давным-давно:

  • Хранимые процедуры с управлением транзакциями появились в PostgreSQL 11 (2018). В T-SQL процедуры есть с самых первых дней.
  • MERGE появился только в PostgreSQL 15 (2022). В SQL Server он есть с 2008 года.
  • Виртуальные генерируемые столбцы новы в PostgreSQL 18. В SQL Server вычисляемые столбцы есть десятилетиями.
  • OLD и NEW в RETURNING (PostgreSQL 18) — ответ Postgres на предложение OUTPUT inserted/deleted в T-SQL.
  • Временны́е ограничения (PostgreSQL 18) — шаг к темпоральным таблицам, которые SQL Server представил в 2016 году.
  • Аутентификация OAuth 2.0 (PostgreSQL 18) — это единый вход, который SQL Server получает через Active Directory и Entra.

Каждый релиз приближает Postgres к SQL Server, но оставшиеся пробелы решают судьбу реальных проектов, и самый большой из них — CI/CD. Без стандартного способа описать базу данных в системе контроля версий и развернуть её из конвейера каждое изменение обходится в скрипты миграций, написанные вручную. Для команды, которая хочет, чтобы база данных определялась её исходными файлами, это серьёзный недостаток, который может стать решающим.

CI/CD и контроль версий: главная победа SQL Server

Это сильнейшее преимущество SQL Server над Postgres, и первое, что я бы взвесил.

В SQL Server база данных — это проект в системе контроля версий. Таблицы, процедуры, представления и триггеры лежат в виде обычных файлов CREATE, а инструменты (проекты баз данных SSDT, sqlpackage) сравнивают этот проект с работающей базой и сами генерируют развёртывание. Вы редактируете желаемое состояние, а инструмент вычисляет изменение. Он напрямую встраивается в Visual Studio, Azure DevOps и GitHub Actions.

У Postgres нет стандартного аналога. Основной процесс — скрипты миграций: на каждое изменение вы вручную пишете пронумерованный скрипт, который переводит базу из одной версии в следующую, и храните их все навсегда. Такие инструменты, как Flyway и Liquibase, могут применять эти скрипты автоматически из конвейера, но каждый из них человек всё равно должен написать вручную до коммита. В SQL Server вы коммитите желаемое состояние, а конвейер сам вычисляет и разворачивает изменение. Инструменты на основе состояния, сравнивающие файлы с работающей базой, существуют (например, Atlas и pg-schema-diff), но они моложе, менее распространены и не являются первичным решением. Для хранимых процедур поверх этого нужен собственный шаг пересборки.

Если вы хотите, чтобы база данных определялась одними только исходными файлами, и не можете позволить себе вручную писать и поддерживать каждый скрипт миграции, SQL Server — более безопасный выбор.

Эти цены приблизительные. Я взял их из сторонних обзоров, а цена хранилища Postgres — моя собственная оценка (около $0,115 за ГиБ-месяц). Прежде чем принимать решение, проверьте калькулятор цен Azure.

Что вы платите и что чувствуете, когда вызовов становится больше. Цены Azure SQL в $5 и $15 фиксированы для уровня. Вы платите их независимо от того, получает ли база один вызов в день или миллион. Ограничивает вас ёмкость. Когда вызовам нужно больше, чем 5 или 10 DTU уровня, запросы замедляются, и вы решаете это переходом на более высокий уровень, а не оплатой за каждый вызов.

Postgres работает так же в плане цены, но на пределе ощущается иначе. Цена B1ms тоже фиксирована за час, независимо от числа поступающих вызовов. Но B1ms — это «burstable» сервер, рассчитанный на базы, которые в основном простаивают. Пока он простаивает, он копит кредиты, как банковский счёт, а в напряжённые моменты они тратятся. Если он остаётся занятым слишком долго, кредиты заканчиваются, и сервер может перестать отвечать. Решается это так же: переходом на большее число vCore, что, по словам Microsoft, занимает секунды. То есть в обоих случаях больше вызовов не повышает счёт. Они толкают вас на более высокий уровень, а повышает счёт именно он.

Бесплатное предложение и serverless — исключение. Они берут плату за фактически использованные вычисления, посекундно, поэтому частота вызовов влияет напрямую: частые вызовы не дают базе заснуть и расходуют бесплатный лимит.

Для этой нагрузки ответ зависит от того, сколько часов в день база бодрствует. Если приложение будит базу на несколько минут и затем затихает, бесплатное предложение это покрывает. Если месячный лимит исчерпан, вы выбираете между паузой базы до следующего месяца и оплатой по стандартным тарифам.

У Postgres в Azure есть нижняя граница цены. B1ms стоит около $12 в месяц только за вычисления, то есть примерно $144 в год до учёта хранилища и резервных копий, независимо от того, пользуется ли им кто-нибудь. Аналога автоматической паузы serverless я не нашёл. Гибкий сервер можно остановить, но Azure запускает его снова автоматически через 7 дней, если вы не запустите его сами раньше. Уровень burstable также предназначен для нагрузок, которые простаивают или остаются ниже базового уровня: если CPU остаётся высоким, кредиты заканчиваются и сервер может стать недоступным, а Microsoft описывает этот уровень как предназначенный в первую очередь для непроизводственного использования.

Две вещи могут изменить картину:

  • Совместное использование. Один сервер Postgres может содержать много баз данных, поэтому если все ваши проекты на одном сервере, эти $12 делятся. Бесплатное предложение SQL Server даётся на каждую базу данных.
  • Постоянная нагрузка. Если приложение обращается к базе круглосуточно, бесплатный лимит SQL (около 28 часов одного vCore) быстро заканчивается, и вы платите по стандартным тарифам serverless. Актуальной посекундной ставки я не нашёл, поэтому перед решением посчитайте оба варианта в калькуляторе Azure при вашей реальной нагрузке.

Итог: Postgres не дешевле. То, что он дешевле, — распространённый миф. Программное обеспечение бесплатно, но в управляемом облачном сервисе вы платите за вычисления и хранилище, а не за лицензию, и лицензия SQL Server в любом случае включена в его цену. При 20 ГБ самый дешёвый вариант SQL Server не хуже Postgres при любом уровне использования: бесплатно примерно до 2 часов активности в день, затем Standard S0 за около $180 в год против примерно $190 у Postgres. Разрыв на S0 невелик, так что считайте это в лучшем случае примерно равенством для Postgres, но никогда не явно дешевле. О бесплатных предложениях, которые это делают возможным, см. Hunting Freebies in the Clouds, где сравниваются бесплатные предложения по базам данных и вычислениям у Azure, Google, AWS, Oracle и Cloudflare.

Практический способ решить

Я бы выбрал Postgres, когда:

  • База данных небольшая и состоит в основном из таблиц и представлений, которые никогда не меняются и не развиваются.
  • Лицензирование — заметная статья расходов, или вас поджимают по ядрам.
  • Вы хотите запускать одну и ту же базу данных в любом облаке или на ноутбуке.
  • Ваша команда уже знает Postgres или хочет его освоить.

Я бы выбрал SQL Server, когда:

  • Ваша схема SQL часто меняется, а CI/CD важен: вы хотите, чтобы база данных была описана в системе контроля версий и разворачивалась из конвейера без скриптов миграций, написанных вручную.
  • Значительная часть вашей бизнес-логики будет жить в хранимых процедурах.
  • Вы хотите, чтобы SSIS, SSRS и SQL Agent были частью платформы.
  • Компания привержена стеку Microsoft, включая Fabric и Power BI.

Если вы сомневаетесь, сначала взвесьте CI/CD.

Вердикт

Postgres можно использовать для крошечного проекта с базовыми потребностями в хранении данных. Для всего, что больше, выбор зависит от задачи, от возможностей, которые нужны вокруг базы данных, и прежде всего от вашего процесса CI/CD, где SQL Server выигрывает наиболее явно. Если вы хотите сделать push коммита и чтобы база данных развернулась сама, начните с SQL Server.
