我的简短回答是:把塑造数据的逻辑放在数据库里,把应用代码留给真正处于数据库之外的事情。

几十年来,这一直是软件领域最激烈的争论之一。一派把存储过程视为所有数据转换逻辑的天然归宿,另一派则干脆禁止使用。开发者论坛上满是抱怨:有人仅仅因为把逻辑写进了存储过程,代码评审就被驳回,或者工作遭到批评。

AI 辅助开发改变了这场争论的基调。AI 助手不会站队,而是根据理由逐个权衡每种情况。令人惊讶的是,如今经常是 AI 自己建议使用存储过程,并解释原因:基于集合的处理、原子性变更、清晰的安全边界。本文接下来的内容,就是这种逐案分析的推理。

存储过程物有所值的地方

我经常编写和审查 SQL 与应用代码,对两边的教条都不认同。当逻辑确实是关于数据本身的陈述,而不是关于数据的呈现或可视化时,存储过程就是合适的工具。

  • 基于集合的处理。用一条 MERGE 移动一百万行,胜过把它们通过网络拉出来、在 C# 或 Python 里循环处理、再推回去。
  • 没有网络往返。应用代码中的业务逻辑必须把所需的每一行从数据库取出,再把每个结果发回去保存。这会让流量翻倍,为每一步增加延迟,并随每次调用成倍放大。存储过程在同一个地方读取、计算和写入,只有最终结果会经过网络。隐藏的代价出现在服务器端。成千上万次小调用意味着成千上万个并发连接,每个活动请求都会占用一个工作线程。工作线程上限与核心数挂钩,因此线程耗尽时 CPU 看起来依然很空闲。唯一的办法是仅仅为了维持连接而购买更多 vCore,最终数据库的账单反而比把逻辑放在数据库内部更高。
  • 跨多张表的原子性变更。必须作为一个整体要么成功要么失败的事务,放在数据所在的地方最安全。
  • 调试。你可以用真实数据运行一个存储过程,逐步执行,并用普通的 SELECT 检查每个中间结果。复现一个缺陷,只需用相同的参数重新运行。而要在应用的控制器、服务、ORM 和日志中追踪同一条规则,要困难得多。
  • 版本控制与部署。微软的 SQL Server 数据库项目多年前就解决了这个问题。存储过程像其他代码一样存放在 Git 中,GitHub Actions 流水线会把项目与目标数据库比较,只应用有变化的部分。部署一个存储过程往往比发布一次应用版本更小、压力也更小。
  • 数据完整性。强制执行不变式的约束、触发器和存储过程,能让数据免受每一个客户端的破坏,包括那些没人记得是谁写的客户端。
  • 权限。对存储过程授予 EXECUTE 权限,同时禁止直接访问表,是一条清晰且可审计的安全边界。
  • 批处理与 ETL 作业。在数据旁边加载、去重和核对文件,既快又简单。

它们不合适的地方

存储过程并非没有代价。以下是真实存在的几项。

  • 扩展不均衡。增加应用服务器很便宜,而增加数据库 CPU 是最贵的扩容方式。不需要紧挨着数据的、CPU 密集型的计算,更适合放在代码里。
  • 可移植性丧失。依赖特定方言的过程式代码会把业务绑定到单一供应商,迁移就变成了重写。
  • 知识被孤立。能熟练阅读过程式 SQL 的开发者不多,规则最终只有一两个人懂。多年来「不要把逻辑放进数据库」的建议,让真正的 SQL 专家变得极为稀缺。拥有他们的公司应当把他们视为关键人才,并努力留住他们。

AI 辅助开发带来的改变

AI 编程工具已经消除了过去针对数据库代码的大部分反对理由。

AI 助手可以重构存储过程、追踪整个模式中的依赖关系,审查 SQL 的轻松程度不亚于审查应用代码。当你的 AI 编程助手已经在做这项工作时,再购买专门的 SQL 代码分析器就没什么意义了。

AI 同样非常擅长编写和调优基于集合的 SQL,因此那些应当放在数据库里的数据密集型工作,现在比过去更便宜、更容易做对。

还有一点需要注意。请把真实的模式、触发器、权限和数据量提供给助手,因为孤立阅读的存储过程可能看起来正确,却仍会在生产环境中出错。

一个真实案例:逻辑放在数据库里,成本依然很低

把逻辑放在数据库里,并不意味着每次页面浏览都要访问数据库。stas.club 上的 Crypto Jobs 页面展示了如何两者兼得。

职位信息存放在 Azure SQL 数据库中,其中的存储过程判断哪些职位与加密货币相关,并整理出列表。这是数据逻辑,所以留在数据库里。但一个任何人随时都能加载的公开页面会让数据库一直保持唤醒,而一个需要被唤醒的无服务器 Azure SQL 数据库既花钱,又可能让页面卡上几分钟。

所以这个页面从不接触数据库:

  1. Google Cloud 上的每日定时任务调用网站的 Web API。任务本身不含业务逻辑;工作由 API 及其背后的存储过程完成,因此同样的刷新也可以手动运行。
  2. API 运行存储过程并返回成品列表。
  3. 任务把该列表作为 JSON 文件写入免费层的 Cloudflare R2 存储桶。
  4. 有人打开页面时,网站从 R2 读取准备好的文件。数据库完全不参与。

结果是每天只有一次数据库调用,而不是每位访客一次。规则仍然集中在一个地方,页面瞬间加载,数据库在一天中的其余时间可以休眠。

做决定的经验法则

先问这段逻辑是关于什么的。如果它描述的是数据必须如何被塑造、移动或保护,就属于数据库。如果它需要数据库之外的东西,比如实时外部数据、网络调用或用户界面,就属于代码。

逻辑更合适的位置原因
批量加载、合并、去重存储过程基于集合,紧挨着数据
引用完整性和唯一性规则约束对每个客户端都生效
行级访问控制数据库权限只有一个强制执行点
定价、折扣、评分存储过程基于集合,对所有使用方给出同一个答案,易于检查
工作流和审批状态存储过程允许的状态转换在一处强制执行并可审计
需要实时数据的规则(市场价格、API 数据源)应用代码数据位于数据库之外
调用外部服务应用代码数据库不应发起网络调用

结论

存储过程是业务逻辑的好归宿,而不是坏归宿。关于数据本身的规则,例如评分、定价、工作流状态和完整性,应当放在数据旁边。在那里,它们基于集合运行,为每个使用方给出相同的答案,而且易于检查。应用代码则留给真正处于数据库之外的事情:实时外部数据、网络调用和用户界面。

仍然会有一些工程师不同意,其中少数人确有理由:团队缺乏 SQL 技能,或者数据库的计算资源已经到了上限。对其他所有人来说,先问一条规则是关于什么的,然后把它放到那些数据所在的地方。请有意识地做这个选择,而不是出于习惯。
